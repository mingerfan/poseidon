## 2. 当前 Level 的含义和变化规则

当前模型计算使用 **L1～L5**。Level 表示密文所在的模数链位置，与网络有几层无关；在本执行计划的计数约定中，L 对应 L+1 个 Q 模数。

- **乘法与 Rescale：**乘法本身保留 level，将常见的 scale 从 2^43 提高到 2^86；随后的 Rescale 消耗一个 level，并将 scale 恢复到约 2^43。
- **加法和旋转：**操作本身不消耗 level，但加法两侧可能需要先对齐 level。
- **ModSwitch：**将分支降到兼容的 level，一次可以下降多个 level。
- **重线性化：**将密文乘法产生的三个分量变回两个分量，本身不改变 level。
- **自举：**当前计划中全部 604 次自举均为 **L1 → L5**，输入和输出均为两个分量、scale_log2=43。

因此，一个 RMSNorm 或 Softmax 内部可以多次经历“计算消耗 level → L1 自举恢复到 L5 → 继续计算”。不能给整个子层只标一个固定 level，也不能用子层入口和出口的 level 差计算自举次数。

## 3. 各计算阶段的 Level 安排

下表以第二个 token 的两个 block 为主。表中的 level 是编译后跨阶段的数据边界；编译器会共享输入准备操作、复用明文，并穿插调度不同分支，因此部分边界会出现多个 level。

| 计算阶段 | 当前主要 Level 路径 | 说明 |
|---|---|---|
| Block 输入 | L5 | 外部输入或上一个 block 的残差输出 |
| Attention 前 RMSNorm | L5 → L2 | 内部执行多次自举 |
| Q/K/V 投影 | 归一化结果 L2 → 主要投影输出 L5 | 投影之间存在共享的 L4 输入准备结果 |
| RoPE | L5 → L5 | 内部仍包含 level 消耗和自举 |
| Attention 点积及加权聚合 | 跨阶段涉及 L2、L3、L4、L5；送往 O 投影的结果为 L2 | 两个 block 的具体分支对齐略有不同 |
| Softmax | L3 → L3 | 两个 block 各计划 168 次自举，入口出口同级不代表内部没有消耗 |
| O 投影 | L2 → L1 | 后续进入残差相加 |
| Attention 残差 | L5、L1 对齐至 L1，相加后自举至 L5 | 每个 block 此阶段 1 次自举 |
| MLP 前 RMSNorm | L5 → L2 | 内部执行多次自举 |
| Gate / Up 投影 | L2 → 主要输出 L5 | Gate 与 Up 之间也有共享的 L4 准备结果 |
| SiLU | 第一个 block：L5 → L3；第二个 block：L5 → L5 | 分别计划 12、10 次自举 |
| Gate 逐元素乘积 | L3、L5 或 L5、L5 → L2 | 包含对齐、乘法和 Rescale |
| Down 投影 | L2 → L1 | 后续进入残差相加 |
| MLP 残差 | L5、L1 对齐至 L1，相加后自举至 L5 | 每个 block 此阶段 1 次自举 |
| 最终 RMSNorm | L5 → L2 | 计划 11 次自举 |
| LM head | L2 → L2 | 计划 1 次自举，生成全部词表 logits |
| 最终输出整理 | 全部为 L2 | 包括 KV 输出的 level 对齐 |

## 4. 明文与密文的 Level 分布

以下统计覆盖完整执行计划中的唯一值。明文数量指编码后的明文对象，密文数量包含输入、中间结果和输出；均不是原始权重标量数或 token 数。

容量单位为 GiB（2^30 字节），数值显示至三位小数。

| Level | 编码明文数量 | 明文系数容量 / GiB | 密文数量 | 密文系数容量 / GiB |
|---|---:|---:|---:|---:|
| L1 | 14 | 0.014 | 8010 | 15.645 |
| L2 | 51 | 0.075 | 20022 | 58.896 |
| L3 | 35 | 0.068 | 55889 | 218.977 |
| L4 | 6319 | 15.427 | 8154 | 40.349 |
| L5 | 2 | 0.006 | 621 | 3.650 |
| **合计** | **6421** | **15.590** | **92696** | **337.516** |

**全部明密文系数容量合计为 379144634368 字节，即约 353.106 GiB。** 合计使用原始字节数计算，不使用已四舍五入的表格值相加。

### 4.1 明文在哪个 Level 编码、占多大

明文并非全部在输入所在的 L5 编码，而是按照具体使用位置准备：

- 6421 个编码明文中，**6319 个位于 L4**，对应约 **15.427 GiB**。
- 全部编码明文合计约 **15.590 GiB**，均使用 scale_log2=43。
- 其中 **LM head 使用 5120 个 L4 编码明文，系数容量为 12.500 GiB**，是明文容量的主要来源。
- 不同阶段可复用同一编码明文，逐阶段的“使用明文数量”存在重叠，不能直接相加代替全局去重统计。

### 4.2 密文为什么集中在 L3

当前大量线性计算使用 L4 的密文和编码明文相乘，再经 Rescale 得到 L3；后续旋转、加法仍会生成 L3 的中间结果。保留全部中间结果时，这些值会持续累积，因此 **L3 密文系数容量约 218.977 GiB**，是最大的单项。

密文一般有两个分量；密文乘法后、重线性化前暂时有三个分量。当前计划包含 723 个三分量密文值：L2 为 162 个、L3 为 338 个、L4 为 219 个、L5 为 4 个。上表已按实际分量数计入容量。

## 5. 容量计算口径与结论边界

当前 CPU 系数按 uint64 存储。单个值的系数容量估算为：

```text
容量（字节）= 65536 × 8 × (Level + 1) × 分量数
明文分量数 = 1
普通密文分量数 = 2
密文乘法后的临时分量数 = 3
```

例如，一个 L4 编码明文占 2.5 MiB，一个普通 L4 密文占 5 MiB，一个普通 L3 密文占 4 MiB。

**353.106 GiB 是全保留策略下模型值的系数载荷估算，不是实测 RSS，也不是 GPU 显存峰值。** 实际运行还需要评估密钥、自举临时工作区、对象管理和内存分配等额外开销；运行到某一时刻的已分配容量也不等于完整计划的累计容量。

当前可以确认的结论是：模型通过 L1 → L5 的自举反复补充计算所需的 level；主要自举负担来自 Softmax 和 Attention 核心计算；明文集中在 L4，密文保留容量集中在 L3。完整 CPU CKKS 已通过上述误差阈值，实测 RSS 峰值约 382.08 GiB；此结果对应两层、两 token、合成权重和全保留策略，不代表 GPU 显存或完整 24 层结果。

## 6. 全保留模式下的实测峰值内存

### 6.1 实测结果与载荷对照

| 统计项 | 字节数 | GiB | 含义 |
|---|---:|---:|---|
| 编码明文系数 | 16,739,467,264 | 15.590 | 最终保留对象的实际系数数量，与计划估算一致 |
| 密文系数 | 362,405,167,104 | 337.516 | 输入、中间结果及输出的实际系数数量，与计划估算一致 |
| 明密文系数合计 | 379,144,634,368 | 353.106 | 模型值的数据载荷 |
| **探针进程峰值 RSS** | **410,257,731,584** | **382.082** | 操作系统记录的进程最大常驻内存 |
| 峰值 RSS 减系数合计 | 31,113,097,216 | 28.976 | 两项统计的差值，不是某一种工作区的独立测量 |

RSS 由测试探针内的 `getrusage(RUSAGE_SELF).ru_maxrss` 读取，在 Linux 上从 KiB 乘 1024 转为字节。它是探针进程从启动到测量时的历史峰值，覆盖读取计划、生成密钥、模型计算和最终解密检查；不是某一时刻的整台服务器已用内存，也不是 `/usr/bin/time` 包装进程的内存。

本次使用 `AllValuesAfterRun`，计划不含 Release 或输入复用，最终保留 **99,117 个模型值**。“不释放”指这些模型中间结果保留到执行完成；自举函数内部临时缓冲区仍按后端自己的生命周期管理，并非禁止程序释放任何内存。

运行期间看到的数十 GiB 或约 100 GiB 只是当时的占用。随着旋转、加法、乘法等结果不断积累，内存会继续增加，不能将中途采样值当作完成后的峰值。

### 6.2 为什么占用较大

1. **单个密文对象本身很大。** N=65536 时，普通 L3 密文有 2 个分量、4 个 Q 模数，系数即占 4 MiB；896 个有效数据槽并不意味着只分配 896 个数。
2. **全保留策略累积大量结果。** 共 92,696 个密文值，旋转和加法也会生成独立结果；占用最大的 L3 密文共 55,889 个，约 218.977 GiB。
3. **权重编码后会放大。** 编码明文存储在 CKKS 多项式及各模数分量中，容量不能用原始浮点权重文件大小代替。LM head 的 5,120 个 L4 明文占 12.5 GiB。
4. **RSS 还包含模型载荷之外的分配。** 评估密钥、Context、自举临时空间、明文 bundle 缓冲、计划元数据及分配器等都会占用内存。不同对象的峰值未必同时出现，因此不能把上表约 28.98 GiB 的差值全部归为自举工作区或密钥。

本轮并未逐项独立测量这些额外分配，也没有证明哪一次自举或哪个阶段触发了全程最高 RSS；报告只给出已核实的进程峰值和对象载荷。

### 6.3 当前使用的优化与适用范围

本次结果已经包含 `packed_linear.py` 的行打包 Linear，以及 `packed_lm_head.py` 的全槽位对角线分组 LM head。自动自举使模型主体反复在 L1～L5 计算；不能通过累积一条很长的模数链来解释本计划的容量。

本轮仍保留所有模型中间结果，因此 **382.08 GiB 是该模式的测量结果，不是释放模式所必需的内存**。如采用最后使用后释放，必须启用匹配的编译和运行设置，并重新测量峰值。锁定的 Runtime `f7e9115` 需要计划中存在显式 Release，单独把无 Release 计划的运行模式改成 `FinalOnly` 不会释放其中间对象。

这次在 CPU 上测量，不能把 382.08 GiB 当作 GPU 显存峰值；GPU 的系数表示、临时空间、密钥和内存复用策略须在目标后端实测。它也不能替代 24 层模型、长序列或预训练权重的测试。
