# 问题2与问题3：level及Boot的Python模拟归因

2026-10-30。按用户要求切换为Python节点模拟，停止整网重编译。模拟只传播scale/level并搜索区域间的Boot，不执行加密、GPU计算或完整编译流水线。28组配置的计算约0.21秒。

主要结论：在本区域模型中，当前ReLU scale策略相对22Q参考策略，多使用31个ReLU主路径level，连带其它主路径多2个，共33个；Boot为27对18。仅取消Boot对齐的30bit门槛，仍为27次；理想化消除全部入口scale对齐代价，得到23次。因此9次差距不能再与“问题3的4次”相加：4次属于两项交互。

## 模型范围与校准

[simulate.py](simulate.py)从此前保存的真实编译器ReLU trace去除已有管理节点，重建115个算术节点，重新执行当前规则：

- MulCP系数默认编码s40；MulCC相加输入scale；逐实际Q归一化，直到再Rescale将低于s40。
- AddCC先按整数类型上调，再按实际scale对齐，level取两输入较低前缀。
- ResNet20用19个ReLU、19个主卷积、9个残差合并、2个投影支路及pool/FC尾部构成。
- 当前ReLU展开为P1/P2/P3/尾乘4个区域；参考ReLU使用已验证的Q31/s40→Q9/s40合同。
- 为隔离问题1，所有对照的卷积都使用同一个联合scale规划抽象：主卷积CP最长串行深度2、投影1、末端3，每条CP路径至少40bit编码精度，按实际模数求达到s40所需的最少Q。不逐个重放全部卷积乘积，也不计每个分支的GPU操作数。
- 初始Q34/s40，Boot出口Q31/s40、入口Q6/s40，模数数组与手动Q50/P25完全相同，每次工作预算25Q。

四个单ReLU检查点均与已有真实trace的Q及浮点scale吻合（误差<1e−8）：P1为Q25/s60.069203，P2为Q17/s41.758472，P3为Q8/s68.826002，尾乘为Q6/s44.845572。

Boot在区域输入处选择是否刷新，保留有界候选。宽度8/32/64/256均得到相同的18/27/23计数。宽度1会剪掉当前策略的可行续接，已记录为模型搜索失败，不当成物理不可行。此搜索不是生产DaCapo实现。

模型复现了18与27的总次数，但切分位置和细账不同：模型基线有54个入口Rescale，而真实27次计划是48个。因此下文严格区分“模型归因”与“对真实计划固定位置做约束模拟”，不将模型细账当成原编译器的精确分账。

## 问题2：区域scale传递的level损失

问题2在本实验中的含义是“当前ReLU区域scale/level传递”与“已验证22Q参考合同”的整体差异，包括编码scale、分支对齐和多项式内Rescale布局；不是只改一条整数取整语句的独立消融。

以下细账取候选宽度32的模型解，统计跨19个ReLU的主路径level使用量。内部发生Boot后，按重置后的状态继续累计，不能只用初始Q减最终Q。

|项|22Q参考策略|当前ReLU策略|差值|
|---|---:|---:|---:|
|19个ReLU区域|418|449|+31|
|主卷积，含stem|57|58|+1|
|pool/FC尾部|4|5|+1|
|残差合并主路径|0|0|0|
|主路径算术合计|479|512|+33|

投影支路两者均为4个level，因其与主路径并行，没有再次加进主路径合计。

19个ReLU的增量分布是8个多1级、10个多2级、1个多3级，共31级。单独从Q31/s40、不插内部Boot的标准ReLU是25Q对22Q，局部差3Q；全网不能机械乘成19×3，因为中间Boot会重置scale并改变后继Rescale数。

在现有入口约束下，该模型的Boot为27对18，即问题2区域策略改变对应净+9次。它包含了因scale错配而产生的入口对齐与切分碎片的连带影响，不能再把所有入口代价作为独立Boot数重复相加。

一个可闭合的level账本（宽度32的模型解）：参考策略主路径479级、入口丢弃0级、最终Q5；当前策略主路径512级、入口合计丢弃188级、最终Q9。每次Boot从Q6恢复Q31，新增25Q，因此：

```text
额外算术33 + 更早切分丢弃188 + 末端多余4 = 225 = 9 × 25
```

这188级是全部Boot入口处Rescale与ModSwitch的合计，描述各段未充分利用的容量；不是额外188级算术深度。不能把33/25直接换算成新增Boot次数。

## 问题3：完整入口对齐与30bit门槛分开看

### 对真实27次计划固定位置做纯Python约束扫描

[fixed_cuts.py](fixed_cuts.py)读取已保存的27个源状态，以实际素数重新求入口对齐，不执行编译器。结果如下：

|单位明文最低编码s|入口Rescale级数|入口ModSwitch丢弃级数|合计下降level|
|---|---:|---:|---:|
|30，原规则|48|123|171|
|24|46|125|171|
|20|45|126|171|
|15|38|133|171|
|8|36|135|171|
|0，理论对照|27|144|171|

原规则21个入口需要2Q、6个需要1Q，共48个对齐level。取消额外精度门槛后，当前27个状态各需1Q，共27级；保守门槛多产生21个Rescale级。

但固定源状态和入口Q6时，**减少的21个Rescale会由21个ModSwitch下降代替，净level下降仍为171**。问题3的关键影响是“能否把切分点向后移”：两Q对齐通常要求至少Q8，一Q只要求Q7。它不是在固定位置凭空少掉21个总level。

现有27个入口中，只有1个恰好卡在对齐所需的最低Q数，其余26个至少还有2级ModSwitch余量。这解释了为什么放宽精度门槛不一定能少一次Boot；还必须让下一个完整区域或切分点变得可达。

[固定位置扫描](fixed-cut-precision-simulation.json)保留了全部结果和裕量分布。0bit只用于约束消融；其中一个单位明文所需s仅约2.195，不能当作精度合格的部署参数。

### 重规划区域DAG：只放宽门槛，与消除全部对齐代价

|ReLU区域策略|现有30bit门槛|仅取消精度门槛，仍做真实对齐|理想出口已是s40，零级对齐|
|---|---:|---:|---:|
|当前threshold传递|27|27|23|
|22Q参考合同|18|18|18|

“理想出口”是模拟oracle：假设上游已经免费提供s40，只检验还剩多少Boot压力。它没有生成真实CKKS操作，也没有把真实Boot接口改成接受任意scale。将其23次看作已经实现的合法方案是不正确的。

因此问题3有两个结果：

- 只去掉保守的30bit编码门槛：本模型净减少0次Boot；实际固定位置只把Rescale换成ModSwitch。
- 理想化消除全部入口scale错配代价：本次模型找到27→23，减少4次。这表示与问题2相关的改善潜力，仍需要真实scale策略来实现。

## 交互归因，避免9+4的重复计数

按“先理想消除入口对齐，再改区域scale”的顺序，可分为：

```text
当前策略27 → 理想出口23 → 22Q参考18
             −4               −5
```

反过来先使用22Q参考合同，Boot直接27→18，出口已经是s40，随后再消除入口对齐得到18→18。即问题2整体效应为9次，移除入口错配后仍有5次；4次是交互，不是额外再加在9上面。

这里的4+5是本模型按给定消融顺序的分解，不是证明实际编译器的9次差距可唯一分摊为两个固定数字，也不是全局最优下界。
