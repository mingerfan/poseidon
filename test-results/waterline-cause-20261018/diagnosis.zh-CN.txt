当前实现相对原版的剩余性能差距：原因隔离
日期：2026-10-18

结论

已确认当前 Runtime 存在逐项调度产生的额外 CPU 开销。上次修复消除了提交后等待 GPU 完成、固定休眠等问题，但每项任务仍然需要工作线程与主调度器交接。全加载也使用这条路径，因此即使没有按需加载，仍然可能比原版慢。

水位加载还有读取、编码、上传及资源回收等运行时成本。全加载退化和在线准备成本应分别讨论，不能把所有差距都归为“显存不足/PCIe 传输慢”。

本次只创建隔离实验及分析记录，没有修改正式实现。188Server 本次 SSH 持续返回 SOCKSv5 Host unreachable；V100 数字来自之前已归档的真实 GPU 测试，没有声称本次补跑 V100 profile。

一、原版与当前执行路径

原版：每个设备的工作线程连续遍历自己的任务队列，依次提交 A、B、C。CUDA 调用异步提交后，可以继续提交下一项，GPU 按流顺序执行。

当前：主调度器分配 A -> 工作线程提交 A -> 通知调度器并等待 -> 调度器检查状态、释放工作线程、选择 B -> 唤醒工作线程 -> 提交 B。

这不是每项都等待 GPU 完成，但仍是每项都需要 CPU 交接。当前代码 runtime/runtime.hpp 的 run_parallel_tasks 中，worker 在提交后等待 assigned 改变；主循环处理 submitted、release_worker，再分配下一项。此路径未因 waterline_ 为空而跳过。

当前还无条件构建 TaskState/ResourceUsage、排序、分组，并在调度循环 collect_completed。部分 API 调用和 Release 本身也会 collect_completed，增加重复回收/查询。额外准备 worker 即使在全加载下也会创建。

二、CPU 控制实验：直接验证调度机制

使用真实 Runtime，按压力负载相同拓扑构造 MulCP/AddCC/Release，数据替换为标量 token，通信立即完成。没有 CUDA、CKKS 编码、权重文件读取、GPU 事件查询。三个版本使用相同 runner 和静态库，仅替换 Runtime 头文件。

legacy：水位管理引入之前 f7e9115 的原始 Runtime 头文件。
current：之前修复后的当前 Runtime 头文件。
prepared_direct：实验版保留当前 TaskState/排序/分组等构建源码，全加载时绕过中央逐项派发，改为每设备线程连续执行。仅用于单 rank CPU 对照，未作为正式修复，也未验证多卡/MPI/GPU 语义。

每个规模/版本运行 7 次，轮换顺序，每次新进程。63 次均校验算术结果、输出元数据及运算数量。

权重数   执行任务数   legacy在线ms   current在线ms   prepared_direct在线ms
1024     5118         1.841          20.315          4.021
4096     20478        7.230          91.227          14.826
16384    81918        36.131         302.716         72.600
以上均为中位数，具体样本和范围见 local-cpu/summary.json。

4096 权重的工作量与 V100 压力负载相同：8191 项算术 + 12287 项 Release = 20478 项。Release 约占 60%，虽然没有 GPU 算术，也承担逐项派发成本。

4096 权重的进程主动上下文切换中位数：legacy=1、current=40982、prepared_direct=1。计数覆盖整次 Runtime 调用（包含初始化/设置），在线时间只覆盖执行阶段。current 的约两次主动切换/执行任务与源码中的线程交接一致。

这个控制确认中央逐项协调本身就能造成显著退化；移除它后，时间从 91.2ms 降到 14.8ms。prepared_direct 仍比 legacy 的 7.2ms 慢，说明还存在其他新路径的成本。此对照不是严格的“仅元数据”测量，不应把剩余差值全都归到元数据分配。

这些是本地 CPU 调度实验，不是 FHE/GPU 推理延迟，不能用 91.2-14.8ms 直接分解服务器的差距。CPU、GPU 异步重叠及资源模型均不同。

三、真实 V100 压力负载的证据

方案                    在线执行中位数ms
原版全加载              267.295
当前全加载              542.066
当前水位加载            2271.292

前两者没有在线 Prepare，也没有在线 Fence。全加载的编码和上传已经在初始化阶段完成，因此 274.770ms 的在线退化不能解释为按需加载。

原版与当前算子 API 内累计主机墙钟时间的中位数为 149.279ms -> 179.432ms，增加约 30.153ms。在线时间的大部分增量发生在这些算子调用之外。算子外时间仍含 Release、元数据、调度以及最终 GPU 同步/排空，不是纯 CPU 时间或纯 GPU 空闲时间。API 时间也不是 kernel 时间；各项中位数不必相加等于总耗时中位数。

整个 274.770ms 若按 20478 个任务均摊，约 13.4us/任务；这只是量级估算，不是直接测得的每项交接时间。CPU 对照证实了退化机制，尚未在服务器上量出它对 274.770ms 的精确贡献。

V100 的这个负载有本地压力负载的 4 倍权重/任务，服务器是 Xeon E5-2650 v4，本地是 Ryzen AI 9 HX 370；相同 CPU 交接的单位成本未必一致。短 MulCP/AddCC 很容易暴露提交延迟，较重的 GPU 算子则可能在已排队计算期间隐藏它。不能由此判断 V100 算术本身变慢，或把服务器差距完全归于 CPU 型号。

RTX4060 的单独 MLP Nsight 对照也支持控制路径成本：原版/当前相同 16018 个 kernel，名称/grid/block 统计相同，GPU kernel 活跃区间并集约 104.90/104.71ms；cudaEventQuery 从 4992 次增加到 9927 次，API CPU 时间从 2.05ms 到 4.61ms。它只是一个单独 profile，不属于无 profiler 的延迟中位数；整个进程 kernel 间隔可能含 memcpy，不能全部当 GPU 空闲。

四、水位加载额外慢在哪里

V100 当前水位样本均只准备 4096 次，全部 GPU 编码，未使用 CPU 编码；原始 H2D 总量为 256MiB。说明这些权重各准备一次，没有看到权重被反复重载的证据。

中位数：
  原始数据 H2D CUDA 事件区间累计：62.450ms
  GPU 编码 CUDA 事件区间累计：660.498ms
  bundle 读取函数主机累计墙钟：465.839ms
  Prepare API 主机累计墙钟：913.222ms
  消费者等待 CUDA 事件区间累计：169.976ms

这些量互相重叠。CUDA 事件区间还可能包含流调度等待；不能称为编码 kernel 独占时间，也不能把以上数值相加解释 2271ms。bundle 读取函数含校验、复制和转换，OS 文件缓存没有清空，不能称为纯物理磁盘时间。它们表明 PCIe 上传本身不足以解释全部差距，读取/编码、准备流水线和 CPU 控制都要检查。

比较口径是“权重已经准备好的全加载在线执行”对“执行期间准备权重的水位加载”。若看首次 forward，还应把全加载前置编码/上传计入。这个压力负载全加载初始化约 100 秒，GPU 水位方案的整个 Runtime forward 中位数约 2.315 秒；不能由在线 8.5 倍推断首次运行也慢 8.5 倍。

五、与 Qwen 有关的另一个已知瓶颈

本地合成 q_proj 代理负载使用默认 Auto/8（前瞻 8 组），当前版本每次仍有 361 次 CPU 编码、664 次 GPU 编码，CPU 编码主机累计约 1481.414ms。

在线中位数：全加载 1181.942ms；GPU/128 水位 1287.685ms；Auto/8 水位 2691.817ms。

后两项同时改变编码后端和前瞻窗口，不能单独归因于窗口从 8 变 128。但 Auto 路径仍有大量 CPU 编码是实测事实，仅修复 dispatcher 不会自动消除这部分工作。这里没有重新运行完整 Qwen，不能据代理负载宣称完整模型已解决或完全归因。

六、后续实现方向

1. 为全加载恢复每设备工作线程连续提交，避免每项经过中央调度器。
2. 水位调度按批批准可运行任务，worker 连续消费队列；资源额度仍按实际 GPU 完成回收，保持输入生命周期、字节预算和前瞻上限，不能把“已提交”当作“已完成”。
3. 批量回收完成事件，减少每个调度循环及每项 Release 的重复查询。
4. 单独检查 Auto 编码选择和小窗口；提高水位容量本身不能消除全加载也存在的 CPU 交接。
