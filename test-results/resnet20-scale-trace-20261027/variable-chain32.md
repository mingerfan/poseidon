# GPU≤32 bit：手动版优势与变位宽模数链测试

结论：在相同的单素数≤32 bit约束下，手动版主要凭目标 scale 分配、分支合并后的 rescale 和融合执行减少开销。单纯更换模数链，本次可以减少少量 rescale 或 ×1，但尚未找到同时改善 Q 预算并满足精度要求的方案。此前40 bit实验超出目标约束，只能作为规则敏感性诊断，不能视为本GPU场景下的改进。

本次没有修改编译器或正式模数链。实验、编译、GPU运行全部在188Server完成；本机仅保存结果并生成此报告。

## 为什么同样≤32 bit，手动版更省

≤32 bit约束的是单个RNS素数q，不是log₂(scale)。多个≤32 bit素数组成的RNS可以承载s=110、160这样的中间结果，不能因此认定它使用了更宽的GPU素数。

手动版按多项式树为各节点预分配目标scale。叶项系数的明文scale满足`s_plain = s_target_product - s_basis`，让需要相加的分支在乘法后自然对齐；求和、基底校正后再按节点计划rescale。它允许有用的高scale保留到父节点，并不要求每个乘法都立即降到waterline附近。

具体例子是P1/H6：T1支路s=40，明文s≈70.042256；T3支路s≈60.003349，明文s≈50.038907。两项乘积都达到s≈110.042256，直接求和，再一次rescale到80.046312。这一输出正好匹配父节点的另一支路。

当前编译器从默认系数明文s=40开始，局部吸收部分scale抬升，乘法后贪心rescale；直到相加时才解决分支不一致。该H6中，T1乘积先一次rescale到50.000352，T3乘积要两次rescale到50.011472，随后又添加×1对齐；更上层相加还可能再次抬高。这些局部处理不能替代整棵树的scale分配。

在原手动链上，两版主要密文乘法都是27个、CC最长深度都是14；手动版消耗22Q并有5个×1管理乘法，编译器消耗25Q并有42个×1。另外手动实现有融合叶项乘加和基底校正内核，可减少独立GPU操作和数据读写；本次没有单独测量这些融合的加速比。

## ≤32 bit变位宽链筛选

“非固定”在本实验中指不同level可使用不同大小的素数，不再固定为30 bit；每个候选仍预先形成完整数组，运行时不动态换链。环维度65536、源ReLU计算图、系数、编译器可执行文件、waterline=40和输入s=40均保持不变。

一共筛选291个候选，工作区使用24–27个素数，涵盖固定大小控制、不同位宽分布、顺序变化、随机扰动和局部细调。每个q均为实际素数、满足q≡1 mod 131072，全部Q和保留的P都≤32 bit且互不重复。保留原底部6个素数及Boot内部上方19个素数，工作区实际log₂总预算不超过原来的755.466086 bit，素数离散化造成的差值小于0.25 bit。下面两个重点候选与原预算的差值更小，不到0.0004 bit。

271个候选成功完成编译与scale等式检查，20个被编译器拒绝；筛选保留的10份计划通过C++验证。没有一个成功候选在完整ReLU后留够Q，按当前精度规则对齐到Boot的Q6/s=40。这是有限搜索结果，不构成不存在更好模数链的证明。

## GPU实测发现的精度问题

三份计划均在物理GPU2（V100 32GB）上运行真实加密、GPU计算和解密，全部实际Q/P素数≤32 bit。测试是一个完整ReLU，无Boot；输入为−0.75、−0.5、−0.25、−0.125、0、0.125、0.25、0.5、0.75、0.875，循环填满32768个slot。参考值是同一个多项式的明文计算，因此这里的误差不包含多项式近似ReLU本身的误差。

下表第一行是“编译器使用原手动链”，不是执行手工ReLU实现。

|方案|GPU最大绝对误差|精度门槛|是否通过|
|---|---:|---:|---|
|编译器＋原手动链|0.033630883|0.0001|否|
|编译器＋变位宽链 A|0.220769274|0.0001|否|
|编译器＋变位宽链 B|0.087569834|0.0001|否|

降低rescale次数的两个候选都没有带来精度合格的改进，且误差反而增加。因此目前不能把它们当作更高效的可用方案。

主要误差来源已经定位到低scale的×1明文编码。数学上“乘1不改变值”，但编码需要舍入。例如原计划一个×1明文s≈0.038836，scale≈1.0273，编码1舍入为整数1后，所表示的实数约为0.9734，而不是精确的1。这类误差并没有反映在单纯的scale元数据或明文恒等重放中。

我们只对常数明文做`round(value × scale) / scale`量化，再重放同一计划，就能复现GPU主要误差。该模型不包含加密、rescale舍入或噪声；在全部32768个slot上，模型与GPU的最大差距为：

|方案|GPU与常数量化模型的最大差距|
|---|---:|
|编译器＋原手动链|1.56574001e-05|
|编译器＋变位宽链 A|8.69040896e-06|
|编译器＋变位宽链 B|4.608376e-06|

这表明大部分误差来自常数明文量化，而非GPU超出32 bit或模数查表减法错误。换链会改变这些低精度×1的分布，所以次数更少也可能误差更大。

当前更需要改善的是系数的目标scale分配、加减法与rescale的安排，以及×1对齐的编码精度。仅按次数调链，会把数值不正确的计划误选为“优化”。本次没有顺带修改这些编译器规则。
