# 模数链与当前编译器规则之间的额外开销

适用范围更正：本文40 bit对照超出目标GPU≤32 bit的限制，仅用于诊断，不能作为该GPU场景的优化方案。严格≤32 bit的筛选与GPU精度结果见[新报告](variable-chain32.md)。

结论：已经找到可复现的链相关开销。它来自实际素数、整数 scale 对齐和贪心 rescale 规则的相互作用，不能把手动版 22Q 与编译器版 25Q 的全部差距都归因于模数链，也不能把手动链本身判为错误。

实验在 SSH 188Server 上进行，只分析此前同一个输入 s=40 的 15/15/27 ReLU，不含卷积、Stem 或完整网络。编译器可执行文件、源计算图、操作顺序、系数和 waterline=40 保持相同，没有修改编译器。12 个变体全部生成物理 RuntimePlan 并通过 C++ 验证；三份重点计划逐一核对了 57 个主要数学乘法、系数和依赖，并做了 5 个输入点的明文语义重放。这里的 scale 验证与明文重放不检验 CKKS 编码误差、噪声或实际 Boot 数值精度。

原始数据：[results.json](chain-probe/results.json)；同名算子差异：[differences.json](chain-probe/differences.json)；复现脚本：[probe.py](chain-probe/probe.py)、[details.py](chain-probe/details.py)。所有 s 都表示 log₂(scale)。

## 最严格的对照：只重排同位宽的同一批素数

保留所有素数，只用固定随机种子 0 重排 q[9..30] 这 22 个 30 bit 素数，其余位置完全不动。素数集合、每个位置的位宽、输入 Q31/s=40、全部总模数预算和编译器规则均不变。

|项目|原手动链顺序|只重排 30 bit 素数|
|---|---:|---:|
|主要数学乘法|57|57|
|全部分支 rescale 次数|94|91|
|×1 管理乘法|42|41|
|ReLU 关键路径 Q 消耗|25|25|
|ReLU 输出|Q6 / s=44.845572|Q6 / s=43.914568|

这是同一批模数的不同排列就能减少 3 次 rescale 的直接例子；它没有减少关键路径 Q 消耗，因此不能据此声称会少一次 Boot。总共 94 次 rescale 计入并行分支，不能当作深度。

具体改变发生在 P3：

|同名步骤|原链 rescale 次数|重排后次数|原链相对多出的次数|
|---|---:|---:|---:|
|T3 的乘法结果|1|2|−1|
|T4 的乘法结果|2|3|−1|
|H7 的 T3×c1|2|1|+1|
|H6 的 T3×c1|2|1|+1|
|H5 的 T3×c1|2|1|+1|
|H4 的 T3×c1|2|1|+1|
|H1 的根乘法|3|2|+1|
|合计|||+3|

例如原链 P3/H7 的系数乘法 s=111.758472，经过两次 rescale 到 51.826002；重排后对应乘法 s=96.830592，一次 rescale 到 66.875487。变化来自前序实际 scale、整数对齐及阈值的累积，不是后端对某个模数做了错误的减法。

这个重排只是反例，不是最优链搜索。其他重排有的反而消耗 26–29Q；不能据此随意调整原链。

## 总位预算相同，改用更接近编译器默认 scale 的工作模数

原链从 Boot 输入 Q6 到输出 Q31，有 25 个工作素数：22 个 30 bit 和 3 个 32 bit。诊断对照使用 19 个工作素数：18 个 40 bit 和 1 个 36 bit，保留原来的底部 6 个素数和 Boot 内部上方 19 个素数。特别选择这个 36 bit 素数，使工作区、输入活动模数、全部 Q 模数的实际 log₂ 总预算都不大于原链，差别约 0.000005 bit。两边环维度相同；这里没有增加总模数预算。

|项目|原手动链|同总位预算诊断链|
|---|---:|---:|
|工作区实际 log₂(Q) 总和|755.466086229|755.466081257|
|输入活动模数 log₂ 总和|947.394064063|947.394059091|
|全部 Q 模数 log₂ 总和|1544.215730693|1544.215725722|
|输入剩余素数|31|25|
|P1 / P2 / P3 / 尾部 Q 消耗|6 / 8 / 9 / 2|4 / 4 / 7 / 1|
|ReLU 关键路径 Q 消耗|25|16|
|全部分支 rescale 次数|94|60|
|×1 管理乘法|42|36|
|ReLU 输出|Q6 / s=44.845572|Q9 / s=75.609896|
|能否直接按当前规则对齐到 Boot 的 Q6/s=40|失败：没有剩余 Q 完成 scale 对齐|通过：1次 ModSwitch + 2次 rescale|

这里 25Q 和 16Q 的单个模数位宽不同，不能仅用二者相减就宣称节省 9 层相同成本。更可靠的证据是：总模数位预算没有增加、主要数学运算相同，全部 rescale 原语由 94 次变为 60 次，且剩余状态能够完成现有 Boot 输入对齐。

具体例子是 P1/T4：原链对应乘积 s=100.000705，两个约30 bit的 rescale 后成为40.007758；诊断链乘积 s=80.000192，一个约40 bit的 rescale 后成为40.000286。P2/T2 也由 120.138406 → 两次 rescale → 60.168324，变为 82.002830 → 一次 rescale → 42.002915。

原因是当前编译器的系数明文默认 s=40，乘法后贪心 rescale 至再除一个模数会低于40。约30 bit模数经常留下50或60一带的 scale；后续分支汇合又需要抬高低 scale 分支。例如原链 P1/H7 的乘积两次 rescale 后 s=40.007758，为了加余项又用 ×1 抬高约10 bit。这个重复抬高、再次 rescale 的过程可以随模数位宽变化而减少。

Boot 输入对齐另外用物理化 pass 做了隔离验证，输入实际 scale 通过 earth.arg_scales 传入，并沿用最少30 bit的对齐明文精度规则。诊断链从 Q9/s=75.609896 开始，先 ModSwitch 到 Q8，然后编码1（明文 s=39.857540），乘法后 s=115.467435，再依次 rescale 到 Q7/s=75.467498、Q6/s=40。见[物理化 IR](chain-probe/aligned.mlir)。原链的 ReLU 输出已经是 Q6/s=44.845572，没有可用 Q 完成这一对齐，pass 明确拒绝。

这只验证对齐逻辑可以生成合法的 level/scale，并未运行新链下的原生 Boot。新链参数在[诊断 OperatorSpec](chain-probe/operator-spec.json)中；它是实验输入，不能视作已经验证过加密精度的生产配置。

## 哪些开销不能单独归因于模数链

T3 的60.003349被抬高到61，直接原因是整数类型的 ceil(scale) 参与加法对齐；这属于编译器的管理规则，不能全算成链设计问题。换成约40 bit素数后仍然存在36次 ×1，说明换链并没有消除这些规则本身的开销。

此外，原链的32 bit工作段没有被证实是浪费：本次把工作区全部改成30 bit的另一个对照，ReLU反而消耗27Q，高于原链25Q。该对照也减少了约7.33 bit实际模数预算，因此只能用来排除“去掉32 bit段自然更省”的直觉，不能当作严格等预算排名。

现有证据足以确认“当前编译器规则与手动链组合存在可避免开销”，尚不能据此推导完整 ResNet20 的 Boot 次数、加密精度或实际 GPU 用时。更换模数链需要重新验证原生 Boot；保留现有手动链并改进编译器 scale 分配，也是另一条需要单独实测的路线。本次未修改编译器或正式参数。
