连续提交、GPU 优先编码与完成状态竞争修复：最终记录
2026-10-19

实现与原因
全加载按设备连续执行原任务队列，绕过 Waterline 的排序、资源记账和中央逐项派发。CPU/GPU 数据依赖仍由 ValueId 及其 Ready 处理，通信 issuer 的线程约束、显式 Fence 和最终 drain 均保留。
水位模式按完整组批准资源后，批量排入工作线程队列；前台线程不再每项等待主调度器确认。GPU 准备线程发布异步结果，读取下一份已批准权重时与当前编码重叠，只在复用 staging 前等待上份真实 Ready；批次末尾不立即等待。主调度器确认整批准备完成后才派发下一批，缓冲区仍保持互斥使用。完成票据、窗口和字节额度按实际完成回收。
提前 Release 的未使用明文在异步准备发布时不会被重新保留；完成引用仍保护尚未结束的 GPU 工作，防止额度已经归还但显存仍被 Runtime 持有。
Auto 优先选择支持且预算允许的 GPU 编码；临时压力等待已批准工作完成，不因为 CPU 线程空闲就选慢速 CPU 编码。只有 GPU 不支持或已批准工作完成后完整 GPU 组仍放不下，才考虑 CPU。CPU/GPU 显式选择保持不变，失败后不重试或切换后端。
GPU 后端还修复了一个竞争：ReadyEvent 在已被 synchronize 确认完成后，查询仍可能因 try_lock 失败返回 false，导致缓存 staging 被误报为仍在使用。现在以单调原子完成标志保存事实；真正未完成的重叠准备仍明确报错。
Qwen 编译脚本新增 --lookahead-groups 和 --prepare-backend，默认 Auto/128。旧计划保存的窗口不会自动变化；旧 Auto/8 计划运行时会采用新的 Auto 选择策略，但窗口仍为 8。
