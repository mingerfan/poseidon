# Waterline 明文准备：实施、清理与 Qwen-0.6B 验收

**状态：首版实现与小图/压力检查已通过；完整预训练模型前向遇到RMM分配失败，修正中，数值验收尚未完成。更新日期：2026-10-14。**

当前提交、检查日志和未完成项见 [验证入口](../test-results/waterline-20261013/README.md)与 [覆盖审计](../test-results/waterline-20261013/waterline-coverage-audit.md)。同配置完整 HEFT 前后保持审计已通过，见验证入口；完整模型数值验收仍在进行中，尚未通过。本文以下实施、清理和验收要求继续适用；运行中不能报告整阶段完成。

本文是本阶段的实施与交接入口，取代此前的“静态分批、批末 Fence”实施要求。目标是完成简化后的 Waterline、清理被替代的旧机制，并在 `ssh 188Server` 上实际运行完整 Qwen-0.6B。算法、IR、资源约束和前进条件统一见 [Waterline 设计](poseidon-waterline-hybrid-encode-plan.zh-CN.md)；本文规定清理边界、提交方式、服务器操作和最终验收。两份文档共同构成本阶段任务，不再按 Git 历史中的旧计划继续叠加功能。

## 1. 当前代码与本阶段目标

先阅读适用的 `AGENTS.md`，检查当前分支、`git status`、子模块版本及近期提交，以源码确认实际状态。工作区可能有其他工作的未提交修改，不覆盖、不混入自己的提交。

2026-10-10 新增的可选 `stream` 路径采用静态明文分批与 Fence：DaCapo `b60fb1d` 加入分批与 V3 导出，ckks-runtime `d858a84` 加入在线 Encode、Fence 和串行 CPU worker，Poseidon `71dc4fe1` 集成这些修改。当前该静态分批路径已由 Waterline 替换，编译选项为 `eager` 或 `waterline`，默认仍为 `eager`；执行计划没有 Fence 时，runtime 不会自行定期插入 Fence。不要把历史可选分批路径当成原有 runtime 的唯一架构，也不要据此预设必须重写整个执行器。

已有按需读取、在线 CPU Encode、异步上传、完成事件、Release/reuse、多 GPU worker 与二进制计划加载能力已被复用。正式 API 的 `prepare_plaintext_async(desc, slots, fixed_backend)` 已接通 CPU/GPU 完整准备路径，由 runtime 选择固定后端并通过 `prepare_resources` 等接口取得资源上界。当前 V4 Waterline 支持单 rank 管理一张或多张本地 GPU；实验中的固定 degree、设备编号和参数限制不能直接带入生产路径。测试范围统一见上述验证入口与覆盖审计，小图通过不代表完整 Qwen 已经跑通。

本阶段必须完成：

- 保持 HEFT、设备分配和前台计算及密文通信顺序；在后期改写明文准备，补齐计划读写、生命周期和容量检查。
- 支持 CPU 完整 Encode 后上传、上传原始数据后 GPU 完整 Encode，以及简单的动态混合选择。
- 每设备可配置 waterline；按一条指令的完整直接依赖取得资源额度，运行中按真实完成事件回收和补充。
- 将消费者输出、工作区及通信空间与明文准备一起准入；保证已准入任务能够推进，不能只限制 Ready 明文数量。
- 从开始按单机多 GPU 管理设备资源和共享 CPU/Host/pinned 预算，不另造多卡 IR。
- 删除或替换不再需要的旧分批机制；完成真实模型的运行、数值核对和可复现交付。

本阶段不做 Encode 时间模拟、HEFT 联合优化、编译器 CPU/GPU 比例预测、最早/最晚时间锚点、独立 FFT/NTT IR、单份明文跨 CPU/GPU 分阶段编码、纯 Tensor Core 编码或所有实验后端的产品化。先接通满足目标模型的一条 GPU 完整编码路径。

## 2. 清理范围与保留边界

| 内容 | 本阶段处理 |
| --- | --- |
| 旧 `PlanPlaintextStreaming` 的静态划批、自动批次 Fence、批间统一等待 | 用 Waterline 依赖组准入和事件回收替换；可复用依赖收集、大小计算等代码 |
| 仅为旧分批策略服务的选项、执行分支、统计、脚本和测试 | 查明引用后删除或改写，不留下失效入口 |
| 为最近实验计划长期保留另一套批次执行器 | 不作为兼容要求；旧实验计划需要时重新生成，历史对照可从 Git 复现 |
| 在线 CPU Encode、CPU worker、按需读取、有界原始缓存 | 保留有用能力，接入统一资源控制 |
| 异步上传、Ready 事件、资源保活、Release/reuse | 复用并补齐新准备路径的生命周期 |
| 二进制计划及对 Qwen 有用的加载优化 | 保留，不因近期加入而误删 |
| GPU Encode 实现、仍有效的正确性测试 | 提取复用，更新测试目标；不为清理而破坏有效验证 |
| 过期实施步骤、重复设计、无使用方的临时实验入口 | 清理或更新，历史由 Git 保存 |

“最近几天做的”不是删除标准。先形成有源码引用依据的清理清单，再逐项修改；不要整体回退混合提交，不要删除其他人的未提交工作。若旧 Fence 或计划版本还有真实使用方，明确其需求，保留所需语义或一起迁移；不得悄悄忽略旧指令。无需为最近生成的实验数据维护两套完整执行器。

最终文档应只推荐一条 Waterline 实现路径。普通显式 Encode/Transfer 可作为该执行器支持的操作和正确性对照，不因此需要另一套调度框架。程序收尾的 drain、真实通信依赖和确有用途的整体边界同步不能随批次机制一起误删。

## 3. 实现次序与提交

按以下阶段推进，但不要只完成第一阶段就停止：

1. **核对并确定接口。** 确认目标 Qwen 配置、现有算子支持和参数范围，梳理工作空间上界、分配及完成路径，确定最小准备操作和清理清单。
2. **固定 CPU 路径跑通 Waterline。** 接通后期改写、计划 I/O、完整依赖准入、单组容量基线、预算账本和完成回收，替换旧静态分批逻辑。GPU 后端需要的表示从此时就预留清楚，不增加暂时用不到的字段。
3. **接入 GPU 路径与动态选择。** 正式 GPU Encode、目标设备/stream、工作空间与 Ready 发布全部接入；验证 CPU-only、GPU-only 和简单混合。
4. **完成压力测试和清理。** 小水位、延迟注入、生命周期、多 GPU 通信及共享资源测试；删除被替代的分支，更新协议与使用说明。
5. **完整模型验收。** 在 188Server 跑完整 Qwen-0.6B，定位问题直到模型实际产生可核对的结果，交付命令、版本、日志和测量。

重要独立阶段通过相应检查后立即 commit 并 push，不积累成一个最终大提交。只暂存本阶段相关文件。嵌套仓库按 DaCapo → ckks-runtime → Poseidon 的顺序提交并推送，再更新父仓库指针，确保远端可复现。远端分支发生变化时先检查并正常整合，不强制覆盖他人提交。

提交说明包含具体行为变化、验证结果和实际限制。大模型、权重、生成计划和大型 profiler 文件留在服务器工作目录，仓库只保存必要脚本、说明及小型结果摘要；不提交敏感信息。

## 4. 188Server 连接与设备要求

### 4.1 全程保持一条长连接

远程地址为 `ssh 188Server`。开始远程工作前，先建立一条独立、长时间保持的 SSH 连接，并在整个远程编译、测试和取回结果期间保持存活，否则 VPN 可能掉线。

可使用 `ServerAliveInterval=30`、`ServerAliveCountMax=6` 等选项，并让专用 SSH 会话持续运行；这些参数本身不能让已退出的短命令保持连接。远端长任务同时使用 tmux 或等效持久会话保存日志。**仅留下远端 tmux、然后断开所有 SSH，不满足本要求。** 长任务期间持续检查连接和任务进展，全部远程工作结束前不主动关闭保活会话。

### 4.2 GPU 选择

- 单卡测试优先使用**物理 GPU 1**，不要使用存在 ECC 问题的物理 GPU 0。
- 使用 `CUDA_VISIBLE_DEVICES=1` 后，物理 GPU 1 通常映射为进程内逻辑 GPU 0；日志同时记录物理编号、UUID 和逻辑编号。
- **188Server 多卡测试只能使用全部 GPU，不运行双卡或其他子集配置。** 用全部卡构造不均衡进度及真实通信依赖测试；单卡调试与全部卡验证是本阶段的设备配置。
- 若 GPU 0 的 ECC 故障导致失败，保留设备状态和错误日志，区分硬件阻塞与实现缺陷；不能把部分卡的运行冒充全部卡通过，也不能掩盖错误继续宣称完成。

## 5. 模型和已有产物

先定位服务器已有 Qwen-0.6B checkpoint、配置、tokenizer、权重来源、构建目录和产物。最终验收使用完整目标模型及其预训练权重；明确版本、层数、词表、输入 token 和输出范围，建立对应的参考结果。不要把旧产物名字中的“24 层”直接视为与目标 checkpoint 配置相符，也不要缩层、缩词表或换合成权重后宣称完整模型通过。

此前 Qwen24 实验使用合成权重、两个 token 位置、完整 LM head 和 KV 输出。这些产物可供结构回归、容量调查和复用，但不足以验收真实 Qwen-0.6B。旧记录见 [完整编译记录](../test-results/qwen24-dacapo-188-20261010/README.md)。已记录的服务器目录包括：


先核对路径是否存在、配置是否匹配以及版本兼容性，再复用缓存、完整常量 trace 和编译产物。`qwen24-native/traced/trace_qwen24.mlirbc` 是历史原始字节码；省略常量的诊断文本 MLIR 不能作为编译输入。模型或协议不兼容时，应重新生成必要产物，不能以“复用”为由继续用错误配置。

历史单卡密文对象估算已超过单卡容量，不能承诺仅靠明文水位就能解决。以当前目标模型和当前计划重新检查容量：单卡确实不可行时给出资源构成和失败证据，继续推进全部 GPU 的完整运行，不把缩小模型当成最终替代。跨机器扩展、任意密文换出和新的 HEFT 算法不属于本阶段默认范围。

大型产物保存在服务器 `/home` 或指定工作目录，`/tmp` 只放小脚本和日志。保留现有必要的数据校验，不额外引入无用途的全量扫描或全量 RNS 磁盘缓存。

## 6. 验证与验收

详细资源反例见 [Waterline 第 8 节](poseidon-waterline-hybrid-encode-plan.zh-CN.md#8-正确性与验证计划)。至少完成：

- 必要的本地编译、计划格式和原有计算回归；新准备操作确实被 reader、writer、二进制 I/O、Verifier 和执行器共同支持。
- 单卡真实 CKKS 小图：CPU-only、GPU-only、混合选择；数值、level/scale、槽布局及 Ready 等待正确。
- 小水位与延迟注入：完整依赖组确实被阻止后能继续推进；无半组占用、无生产者被等待者堵住、无超预算或提前释放。
- 全部 GPU：通信两端、共享 Host/pinned、设备归属及不均衡进度正确；长期无批末 Fence 仍可回收任务和资源。
- 完整 Qwen-0.6B：真实前向执行并产生输出，使用明确参考结果和事先说明的误差指标/容差核对。若现有算子或 Boot 有近似或特殊执行方式，记录实际语义和参考方式，不隐瞒限制。

编译成功、加载成功、装入显存、完整执行、数值通过分别报告。有限输出和重复运行一致只能辅助检查，不能替代正确性对照。GPU Encode 必须在生产执行路径实际使用，不能只交独立 benchmark；CPU-only、GPU-only 和混合模式的覆盖范围分别列明。

记录冷启动、实际前向耗时、消费者等待、CPU/GPU Encode、H2D 字节与时间、每卡内存峰值、Host/pinned 占用和结束后的回收。启动填充计入冷启动。声称重叠或加速时给出事件/trace 或对照测量，不能用异步 API 名称或 GPU 利用率代替证据。

长任务有正常进展时允许继续运行，不因预设短超时退出就认定任务完成。根据日志判断进度、死锁或资源瓶颈，继续修复。确实需要缺失权重、外部信息或硬件恢复才能继续时，报告可复现的阻塞证据和未完成项；不得把局部测试包装成完整验收。
