# Waterline：编译器与运行时协同的明文准备计划

**状态：设计计划，尚未实现本文的混合调度机制。** 更新日期：2026-10-12。

本版明确实现边界：一个后期物理准备操作、两个进度锚点、一个后端建议；以完成事件驱动的持续滚动预取为默认方式，仅在需要整体等待的边界保留 Fence；采用有界的列表调度与局部搜索。设计从开始就面向单机多 GPU，单卡只是最小验证配置。后文将必要语义、估算信息及后续优化分别说明。

本文承接[明文分批与提前上传计划](poseidon-plaintext-prefetch-implementation-plan.zh-CN.md)，描述下一阶段的方法和实现方针。已有 V3 分批、Fence、CPU worker 与按需读取能力；GPU Encode 已有独立实验，但尚未接入本文的运行时调度。已有验证范围见[实现记录](poseidon-plaintext-prefetch-validation.zh-CN.md)与 [GPU Encode 实验说明](../src/poseidon/tests/gpu_encode/README.md)。本文不把已有微基准结果当作 Waterline 的端到端收益。

## 1. 目标与范围

CKKS 明文编码会把原始权重扩展为较大的 RNS/NTT 表示。预先编码并常驻全部明文需要大量显存；到消费者执行时才编码和上传，又会把准备延迟暴露在关键路径上。CPU 编码主要消耗主机计算资源，并需要上传较大的编码结果；GPU 编码可以上传原始数据，但会与密文计算竞争 GPU 计算和内存资源。

Waterline 将这两条路径纳入同一个准备调度：编译器根据测量驱动的模拟，生成每份明文的准备窗口、推荐编码后端和资源预算；runtime 根据实际执行进度选择完整的 CPU Encode 或 GPU Encode，提前准备近期需要的明文，并将显存占用维持在可配置的水位附近。

本阶段以一份完整明文为调度单位，不将同一份明文拆成 CPU FFT 与 GPU RNS/NTT 等跨设备阶段。两条候选路径为：

```text
CPU 路径：读取原始数据 → CPU 完整 Encode → 上传编码明文 → GPU 可用
GPU 路径：读取原始数据 → 上传原始数据 → GPU 完整 Encode → GPU 可用
```

目标是在内存受控、数值语义正确的前提下，减少前台等待明文的时间，并限制后台准备对前台的干扰。缓存填满率、GPU 利用率和 Encode 吞吐量是诊断指标，不能代替端到端性能目标。

首版面向已知计算图中的权重明文、单机单 rank 的一张或多张 GPU。设备标识、水位、完成进度和准备队列从开始就按设备管理，CPU 与 Host 资源统一协调；先用单卡定位问题，随后用双卡和四卡验证相同机制，不另做一套多卡 IR。跨机器调度、单份 Encode 的 CPU/GPU 阶段拆分、纯 Tensor Core 编码和明文压缩布局均不属于本计划的必要条件。

本文区分三个概念：**滚动预取窗口**是当前允许提前准备的候选范围；**执行区间**是确有 Fence 时两次整体等待之间的计划片段；**Encode batch**是一次 GPU 批量编码的任务数。它们都不等于模型输入的 `batch_size`。Waterline 不要求把模型划成固定执行区间。

## 2. 可用于论文方法部分的描述

### 2.1 核心机制

Waterline 是一种由编译器提供约束、由运行时择机执行的明文准备机制。编译器从计算图提取明文的使用顺序、编码参数、生命周期和设备位置，通过包含编码、传输与并发干扰的成本模型，确定准备窗口及 CPU/GPU 的分阶段分配建议。运行时在这些窗口内持续准备近期将使用的明文，以每设备可配置的显存水位限制提前准备规模；某份数据真正使用完并回收后，即允许补充后续数据，无需等待其他设备或整个区间完成。前台工作到来时停止提交会与之冲突的非紧急准备，接近使用期限的明文升级为必需准备任务，其完成事件控制消费者的启动。各设备独立推进，共享的 CPU、Host 内存及传输链路统一纳入调度。

该方法将三种决策关联起来：**何时准备、在哪里编码、允许提前驻留多少数据**。编译器提供全局依赖和资源边界，runtime 处理实际进度与模拟的偏差。正确性依赖显式的数据就绪和内存生命周期，而不依赖耗时预测完全准确。

```mermaid
flowchart TD
    G[计算图与明文使用位置] --> C[编译器模拟与规划]
    P[编码、传输及并发干扰测量] --> C
    C --> W[每设备准备窗口、后端建议、容量预算与必要边界]
    W --> R[Runtime Waterline 调度器]
    E[每设备实际进度、完成事件与共享资源占用] --> R
    R --> CPU[CPU Encode 后上传]
    R --> GPU[上传原始数据后 GPU Encode]
    CPU --> Q[GPU 明文缓存与 Ready 事件]
    GPU --> Q
    Q --> F[前台密文计算]
    F --> E
    F --> L[最后使用完成后回收额度]
    L --> R
```

### 2.2 研究假设与贡献边界

待验证的假设是：对于明文准备存在可利用提前量、且 CPU/GPU 资源需求随阶段变化的 CKKS 工作负载，受准备窗口和水位约束的混合调度，可以比固定单后端、固定比例或仅按需准备减少端到端等待，同时控制显存和前台响应延迟。

论文的方法重点应放在准备窗口、后端选择、前台资源预留与有界后台提交如何共同工作。可配置的缓存水位本身不足以支撑新颖性主张。相关工作比较和完整实验尚待完成，不预先声称最优调度、零干扰、硬实时响应或已获得加速。

## 3. Waterline 的定义和内存约束

### 3.1 配置水位与实际可用预算

对每张 GPU `d` 分别定义以下量，容量单位统一为字节：

| 符号 | 含义 |
| --- | --- |
| `M_d` | 配置允许该执行器使用的 GPU 总容量，不能超过设备容量 |
| `alpha_d` | waterline 比例，例如 `1/2` 或 `2/3`，满足 `0 < alpha_d < 1` |
| `K_d` | 密钥、参数表等常驻占用 |
| `F_d(s)` | 当前分析窗口 `s` 对应的前台密文对象、算子及通信临时空间预留；窗口边界不隐含同步 |
| `S_d` | 尚未归入前述项的分配开销、碎片及安全余量 |
| `P_d(t)` | 时刻 `t` 已承诺给明文准备和驻留的额度 |

定义明文硬预算和机会性填充目标：

```text
H_d(s) = M_d - K_d - F_d(s) - S_d
W_d(s) = min(alpha_d × M_d, H_d(s))
```

`H_d(s)` 为负，或一个不可拆分的必需工作集合超过预算时，应报告计划不可行，不能靠继续预取解决。`F_d(s)` 必须覆盖允许重叠的前台分配，包括仍在运行的算子临时空间；不能只使用“当前占用”或“最大单个算子的工作区”。

没有批次 Fence 时，前台计算和密文通信也必须采用有限在途提交，并在分配前计入各自预算。否则明文虽不越过水位，前台新输出、接收缓冲和临时空间仍可能无限积压。分析窗口只是估算工具，不能在窗口切换时假定旧任务全部完成；跨窗口仍活跃的资源必须继续计费。固定的保守前台预留可以作为起点，后续再细化为随真实完成事件变化的预留。

`W_d(s)` 是机会性填充上限，`H_d(s)` 是不可突破的容量限制。建议允许临近使用的必需准备超过软水位，但仍严格受硬预算约束；这种情况必须在 trace 中记录。这样不会因水位较低而人为阻止当前消费者执行。若需要严格不越过配置水位，应作为独立策略，其额外等待也要报告。

例如，假设配置容量为 32 GiB、`alpha=1/2`，扣除常驻、前台和安全预留后剩余 18 GiB，则机会性目标为 16 GiB，硬预算为 18 GiB。若后续分析窗口只剩余 12 GiB，则目标降至 12 GiB。这里的数字仅解释定义，不是测量结果或默认推荐值。

### 3.2 先预留，再分配

`P_d(t)` 至少包含以下互不重复的项目：

- 已就绪且仍驻留的明文，以及逻辑 Release 后尚未真正可复用的明文。
- 已获准提交的 GPU 目标缓冲，即使上传或 Encode 尚未完成。
- GPU Encode 输入、输出和工作区的同时存活峰值预留。

每次准入必须先取得额度，再分配和提交。首版让单个调度线程拥有任务状态和额度账本，worker 只返回完成消息，无需为每份明文引入一套并发事务。任务完成后按实际可复用的空间归还额度，输出仍驻留的部分继续计费。不能只统计 Ready 明文，否则多个未完成任务会共同突破水位。

硬约束为 `K_d + F_d(s) + S_d + P_d(t) <= M_d`。它成立的前提是所有相关分配经过一致的记账，且预留覆盖实际峰值；在覆盖不完整时，报告只能称为已计费对象的预算，不能声称总显存有上界。内存池保留的空闲块要区分可复用额度与不能复用的占用，避免漏算或重复计费。CUDA 空闲显存采样仅作核对，不能作为唯一准入依据。

原始数据缓存、CPU 编码结果和 pinned buffer 分别具有 Host 预算。CPU 可以继续提前编码，但不能无限累积结果。多 GPU 还需共享 CPU、Host 内存和 PCIe 带宽预算。

### 3.3 水位变化与前台进展

启动时优先准备最早消费者所需的明文，再在初始化窗口内向 `W_d(s)` 填充。达到目标，或窗口中已无合法候选时，结束初始填充；不为凑满水位跨越依赖或内存边界。启动填充成本要单独报告，并计入冷启动时间。

运行中随消费和回收补充。首版仅使用一个上水位；有额度且存在合法候选就考虑提交，没有则等待下一次进度或回收通知。只有测量表明频繁启停有明显代价时，再增加低水位滞回参数。水位不能代替 GPU 工作量限制。

调整预算前必须检查仍驻留和仍在执行的任务是否满足新预算。不能一面降低水位，一面假设活跃对象立即消失。编译器应提前限制会跨越较小预算窗口的驻留；运行时停止新准入，并等待相关对象正常使用和回收。下一步前台执行所需的资源要提前预留，不能让预取数据反过来堵住负责释放空间的消费者。

机会性任务还应为最近消费者尚缺的明文保留额度。不得让远期缓存占满硬预算，导致当前必需明文无法分配。使用短滚动窗口和近用优先，不做任意缓存淘汰或取消后重新编码；容量不足时暂停新准备，已有使用完成后继续。仅一个窗口装不下，不要求全局拆批；缩短提前量和限制在途规模即可。不可拆分的必需工作集合仍装不下时，才报告容量不可行。已有显式 Fence 的计划继续遵守边界，不默认跨越它预取。

## 4. IR 的具体语义

### 4.1 当前实现的起点

当前代码有三种不同的估算，不能混用：

- [Earth LatencyEstimator](../third_party/ckks-runtime/third_party/dacapo/lib/Dialect/Earth/Transforms/LatencyEstimator.cpp)累加算子成本，用于较早阶段的估算，不模拟异步准备队列。
- [AssignPlacement](../third_party/ckks-runtime/third_party/dacapo/lib/Dialect/CKKS/Transforms/AssignPlacement.cpp)使用 HEFT 风格列表调度，并写出 `dist.schedule_start/finish`。其 `buildGraph` 将 Encode 设为 Host 上时刻 0 已就绪的源，Encode 不进入计算调度节点。因此它尚未模拟在线编码。
- `PlanPlaintextStreaming` 按容量划批，并按 `prefetchBytes` 提前一段 Encode/Transfer；`EstimateRuntimeMemory` 按顺序完成假设统计对象生命周期。它们都不是包含实际异步准备的时间模拟器。

Waterline 需要补充后期的准备时间线分析。早期 scale/boot 优化器和所有数学算子的语义不因此改变。

### 4.2 只新增一个后期物理操作

保留纯数学层的 `ckks.encode`。在完成 placement 和通信物化后，将目标 GPU 的“Host Encode + 直接上传”改写成 `dist.prepare_plain`，结果仍为现有明文类型并具有固定目标设备。以下为设计示意，尚不是可解析的 MLIR 语法：

```mlir
// before
%host_p = ckks.encode {payload = ...}
%p = dist.transfer %host_p {destination_device = 0, ...}
%y = ckks.mulcp %x, %p

// after: point ID 是计划中的完成点引用，不是时间戳
%p = dist.prepare_plain {
  payload = ..., dist.device = 0,
  after = #point10, start_by = #point16, backend_hint = "cpu"
}
%y = ckks.mulcp %x, %p
dist.release %p
// 继续后续计算和预取；此处不自动插入 Fence
```

`prepare_plain` 的语义是：为这个逻辑结果选择一条完整准备路径，最终在指定设备发布可用的 NTT 明文。它允许延迟执行，但不能被当作无副作用常量折叠、跨 Fence 合并或任意移动。为其声明准备和分配的调度副作用；payload 的数学去重仍在更早的 `ckks.encode` 阶段完成。

只增加三个调度属性：`after`、`start_by`、`backend_hint`。内容、结果 ID、编码类型和设备复用已有表达；首次/最后使用从 SSA 和 Release 得到；大小与成本由类型、后端能力表和公共 profile 推导；waterline、Encode batch 和在途提交限制放在计划级配置。首版不重复序列化消费者列表、每任务的四套预算、资源 scope 对象或单独的 NTT 节点。

采用新操作而不是在现有 Host Encode 上增加 `auto`，是为了保持类型和位置明确：CPU 路径产生 Host 临时值再上传，GPU 路径上传原始数据后编码，两者都发布同一个固定 GPU 结果。若仍保留旧的显式明文上传，则 GPU 路径会面对不存在的 Host 结果或多余传输。

两条内部路径的传输都必须计入模拟，封装不意味着传输免费。原有密文、普通明文 Transfer 的语义不变。共享 Host Encode 还有其他消费者时，仅改写满足该模式的分支，不删除仍被引用的原操作；每个目标设备分别有自己的物理准备结果。

`ckks.encode` 与 `dist.prepare_plain` 可以共存于同一份新版本计划。例如一份明文保留 Host Encode 后显式上传，另一份由 Prepare 选择后端。被替换路径只执行 Prepare，原 Encode 无其他使用者时删除，不重复编码。同一个逻辑 Encode 可以对应不同设备或不同使用时段的多个物理 Prepare。当前 runtime 尚不认识 Prepare，新指令的读取、校验和执行必须一起实现；混用设计不代表现有 V3 已经支持它。

### 4.3 最早、最晚和真正的等待分别是什么

| 概念 | IR/运行时表达 | 精确含义 |
| --- | --- | --- |
| 最早允许启动 | `after = 完成点 A` | A 真正完成后才可读取、编码或分配本任务资源；仍须满足容量准入 |
| 预计最晚启动 | `start_by = 完成点 B` | B 完成时，未启动任务升级为必需准备；不是 barrier，也不要求 B 等它完成 |
| 使用前必须完成 | 原有 `%p → consumer` 数据依赖 | 消费者必须等待 `%p` 的 Ready 事件，与预测时间无关 |

`after` 是硬调度下界，`start_by` 是软性能提示。不能把后者实现成“没按时启动就报错”，也不能为了遵守期限读取尚未就绪的数据。初始准备使用 `execution_begin`；计划确有 Fence 时，也可使用该 Fence 的完成点。到期提醒按实际完成点推进，无需每份明文配置独立墙钟定时器。

编译器分析内部仍使用微秒时间：先得到消费者预计需要时间 `D_i`，再从 CPU/H2D/GPU 资源时间线向前寻找完整准备链能够完成的最晚插入位置 `L_i,b`。`D_i - 路径耗时 - 余量` 仅作为无排队时的近似；有资源占用时必须沿对应资源时间线回推，不能只减一个 kernel 的时间。

把所选时间映射到目标 GPU 前台序列中不晚于它的最近完成点，就得到 `start_by`。若允许 CPU/GPU 任意选择，首版取两个可用后端最晚启动时间中较早的一个，换取单个属性和简单运行时。后续若这一保守选择产生明显损失，再考虑按后端推导不同触发点，不先增加两套字段。

例如消费者预计在 12 ms 使用明文，CPU 路径需 4 ms、GPU 路径需 1.5 ms，且假设没有排队，则两条路径的最晚启动时间分别为 8 ms 和 10.5 ms。首版可将公共 `start_by` 映射到预计不晚于 8 ms 的完成点。若 GPU 在窗口内有空闲，可以更早完成；到点还未启动，就必须安排准备，而不是继续等待空闲。

`after` 由执行开始、可用容量及允许的提前量决定，优化器可沿目标设备的完成序列前移或后移它。一次前移只有通过该候选计划的内存检查才可接受；runtime 仍执行容量准入，预测的空间释放不能替代实际完成。

如果推导出的最晚启动早于合法 `after`，说明该方案无法完全隐藏准备延迟。此时令 `start_by=after`，在开放任务时立即提升优先级，并在模拟中保留消费者等待；不要生成矛盾窗口，也不要把单纯的性能不足当成非法计划。硬预算不足时先缩短预取窗口或限制并发；确需整体等待才保留 Fence，不可拆分集合超限则报告错误。

完成点在分析中引用具体操作，定稿后才映射为稳定的计划指令标识。Release 插入、重排或布局导出不能使引用失效。各 Prepare 优先引用目标设备的前台完成点，点所属设备从已有计划位置得到，无需增加一套分布式事件 IR。跨 GPU 的真实数据依赖仍由原通信结果表达。验证器检查锚点存在、属于合法设备进度及显式 Fence 范围、位于首次使用之前，且 `after` 不反向依赖本明文，避免人为制造等待环。不能把所有 GPU 的指令序号合成一个全局完成游标。

### 4.4 持续滚动预取与 Fence 的边界

现有 `dist.fence` 不增加 timeout、deadline 或水位属性。它仍表示：关闭本 rank 当前执行区间的提交，完成区间内已提交的 CPU/GPU/通信工作，交付结果、清理异步引用后，再进入后续执行。它不会隐式释放后续仍使用的值，也不是跨 rank barrier。

Waterline 的默认方式不在每组权重之间自动插入 Fence。窗口随着设备进度推进，某份明文完成最后使用并归还空间后即可补充下一份，不等待其他明文或其他 GPU。例如 GPU0 释放一份明文后可以继续准备，GPU1 尚未结束自己的工作不构成阻碍。

仅在确有整体完成要求的边界使用 Fence，例如现有接口要求全部在途工作结束后才能切换资源配置。程序收尾可以使用原有 drain，不必为了收尾新增一次等价 IR 指令。容量限制本身通常通过等待所需额度解决；水位到达和前台请求均不触发全设备 Fence。

旧 V3 的批次执行器保留原行为，作为兼容路径和实验对照。新滚动执行器必须补上持续的完成回收、任务清理以及前台/通信在途限制后才能减少 Fence，不能只删除旧指令。保留下来的显式 Fence 仍是严格边界。暂不引入 GPU 专属 Fence 或多种屏障；局部等待直接使用现有完成事件。

### 4.5 哪些算子需要改变

| 对象 | 改动 |
| --- | --- |
| `ckks.encode` | 数学语义保持；符合条件的物理 Encode/Transfer 组合在后期改写 |
| 新 `dist.prepare_plain` | 固定 GPU 结果，加两个完成点和一个后端建议，具有调度副作用 |
| `dist.transfer` | 普通传输保持；被准备操作封装的传输在模拟器与 runtime 内部展开 |
| `dist.release`、`dist.fence` | 语义保持；生命周期分析和执行器认识新的准备结果 |
| MulCP、AddCP、Rotate、Rescale 等 | 不加 encode、waterline 或 deadline 属性；继续遵守普通输入依赖 |
| 函数/计划配置 | 存放 waterline、Host/pinned 预算、Encode batch 与在途提交限制，不逐操作复制 |

## 5. 准备算法与估算如何迭代

### 5.1 首版选择：固定前台顺序，优化准备任务

首版保留 HEFT 产生的设备分配和每设备前台相对顺序，只调整准备任务的后端及提前量。这样优化的对象明确，也能与现有计划直接比较。HEFT 的时间戳仅作为初始估计；加入准备后，必须重新计算时间，不能把原时间戳当成不可改变的执行承诺。

模拟器按事件推进，显式记录共享 CPU worker、每 GPU 的计算时间线和 H2D 队列，以及设备间通信、共享链路、依赖和容量。CPU 候选展开成 Encode 后上传编码结果；GPU 候选展开成原始数据上传后 Encode。Host Boot 与 CPU Encode 使用相同 CPU 资源；每种路径使用自己的传输字节数。容量不足时等待可回收事件，消费者在依赖齐全后才能开始。模拟窗口结束不清空资源，不隐式等待其他设备，只有计划中的真实 Fence 才有整体同步效果。

第一步仅把 GPU Encode 插入无前台计算的空隙，或作为消费者必须等待的工作执行，仍允许 CPU/H2D 与前台流水重叠。第二步才加入已测量的 GPU Encode/前台并发组合，并模拟二者的减速。不能将两个 stream 当成两个独立 GPU，也不为“空闲 Tensor Core”假定零干扰。

### 5.2 可实现的启发式

采用“按使用顺序的列表调度 + 受内存约束的空隙插入 + 有界局部搜索”。这是本项目的组合设计，不是某篇论文中已经证明适用于 CKKS 的算法。

1. **构造可行起点。** 复用已有类型、生命周期和容量分析，生成 CPU 按需路径，并采用有限在途提交；若连必需工作集合都装不下，停止并报告。旧分批方案可作对照，但不把它的所有 Fence 自动复制到新方案。空闲提前量与 GPU 路径随后逐步加入。
2. **比较两条候选链。** 按当前模拟的首次使用顺序处理明文，在当前窗口内分别寻找 CPU 链和 GPU 链的可用时段；排除超过容量或工作区限制的候选。最早 GPU Ready 的候选用于给出初始后端建议，但不能仅凭这个局部结果接受整个调度。
3. **做小范围调整。** 每次只考虑更换某个任务的后端，或者将它的 `after` 移到相邻合法前台完成点。对造成消费者等待的任务优先尝试前移；对长期驻留造成容量等待的任务尝试后移。`start_by` 随新的时间线重新推导，不额外搜索一个独立 deadline 变量。
4. **重放并打分。** 将候选交给同一个事件模拟器，比较包含准备、消费者等待、跨卡通信及必要 Fence 的执行结果。局部窗口传出仍活跃的任务、缓冲和依赖状态，不能因为一个窗口结束就假定全设备完成。内存超限候选丢弃；局部完成更早、同耗时但驻留字节时间积更小的调整可进入整图复查，最终按全图完成时间接受。字节时间积指每份缓冲大小乘其驻留时间后求和。
5. **有界迭代。** 在固定大小的局部窗口内比较候选，携带跨窗口存活对象和队列状态。每轮修改后完整重放计划，只保留全局目标改善的方案；连续无改善或达到编译预算即停止。首个实验可限制为最多三轮，这只是工程起点，不是最优性结论。

```text
best = simulate(feasible_demand_plan)
repeat up to R rounds:
    candidate = copy(best.plan)
    for bounded_window in candidate:
        try backend changes and adjacent legal prefetch anchors
        retain locally better changes with the same simulator
    trial = simulate_entire_plan(candidate)
    if trial improves (total_finish_time, residency_byte_time):
        best = trial
    else:
        stop
emit best.plan with recomputed anchors and memory report
```

窗口回放必须包含受影响的消费者和边界存活状态，不能只比较 Encode 本身耗时。局部结果不足以证明全局改善，因此保留完整重放这一轮检查。不能对每个明文都重放数百万节点的全图；限制窗口、轮数与每窗候选数，并测量编译开销。实现首版不依赖 MILP、遗传算法或强化学习框架。

CPU/GPU 比例由最终任务分配统计得到，不再同时搜索一个全局比例参数。runtime 的小幅择机调整也不要求维持精确比例。优化目标是完整执行耗时；不能通过把被阻塞消费者的预计时间不断推迟，让“期限错失消失”来冒充改进。

### 5.3 与现有估算器的连接

从 `AssignPlacement` 提取可复用的算子、通信成本查询，补入完整 CPU/GPU Encode 与工作区测量；使用同一套 profile，避免维护互不一致的两份延迟表。将新的事件回放分析交给 `PlanPlaintextStreaming` 的 Waterline 分支调用，先不重写整个 HEFT 调度器。

候选布局变化后使旧 `dist.schedule_start/finish` 失效，定稿时写回新估计并重新规划 Release/reuse。最终再用这些生命周期和真实准备路径回放一次。保留旧串行对象内存报告作为对照，同时单独输出并发准备峰值，不能把两种估算合并成一个含义不清的数字。

运行时 trace 用来离线校准 profile，再重新编译比较。首版 runtime 不运行完整模拟器，也不在线重新求解设备 placement。如果实验表明固定前台分配严重限制收益，再将准备成本反馈到 HEFT 的 placement 选择；那是扩大的搜索空间，不能在首版声称已经联合最优。

## 6. Runtime 如何执行

### 6.1 机会性填充与必需准备

机会性填充面向窗口内未来会使用的明文：按预计需要时间排序，在目标设备水位、共享 Host 预算和并发预算均允许时准备。GPU 空闲时可以较积极地填充；前台运行时仅使用编译器已允许、经过测量的重叠机会。一张 GPU 到达水位或繁忙，只暂停与它及所争用共享资源有关的准备，不一概停止其他 GPU。

必需准备面向已被消费者请求或到达 `start_by` 的明文：优先取得资源，并推进已有任务。首版先按 `backend_hint` 执行，在任务尚未开始、另一后端受支持且满足资源约束时才允许择机改选；不在运行时重新搜索整张图。任务启动后不迁移、不重复编码。所有后端都来不及完成时，消费者等待并记录原因。

这里的“请求”包含新的前台执行请求和运行中消费者提出的明文需求。收到请求后停止提交会影响前台的机会性 GPU 工作；请求所依赖的准备必须继续推进。CPU 可在自身预算和前台 CPU 需求允许时继续工作。

### 6.2 让路语义与 stream

建议使用独立的前台计算 stream、低优先级 GPU Encode stream，以及有序管理的 H2D stream，通过每份明文的 Ready 事件连接消费者。

CUDA stream 优先级不保证抢占已经执行的工作，也不保证传输优先级。因此，“立即终止填充”定义为**立即停止提交新的非紧急后台工作，在已提交的小段完成后让路**，不表示取消正在执行的 kernel 或复制。参见 [CUDA 异步执行与 stream 优先级说明](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/asynchronous-execution.html)。

runtime 必须限制后台提交量。首版以一份完整 Encode 为不可中断单位，每张 GPU 最多一个在途 GPU 准备任务；在这份 Encode 的完成事件后检查是否继续，不设“整个进程同时只能准备一份”的限制。只在已有测量允许的情况下将单位扩大为小 batch，不一开始实现半成品暂停与恢复。若单份 Encode 的让路延迟已不能满足目标，再研究后端内部的阶段检查点。

让路延迟主要受已提交工作、资源竞争和主机响应开销影响。未获得实际最坏情况界限前，提交预算只是控制手段，不是硬实时保证。H2D 也需限制提交深度和块大小，不能通过低优先级 stream 假定它不影响前台传输。

完整任务启动前预留其峰值工作区，避免执行到中途才等待额外额度。收到请求后允许这个有限任务完成；不调用 stream 销毁或设备重置来尝试取消它。

### 6.3 状态、事件和内存回收

准备任务可采用如下状态；CPU/GPU 中间步骤分别记录在任务内部：

```text
候选 → 已准入并预留资源 → 准备中 → GPU Ready → 使用中 → 可回收
                       ↘ 失败，通知所有依赖者并安全清理
```

每个结果只允许一个准备任务取得所有权。取消尚未提交的候选可以立即归还其未使用额度；已提交任务必须等完成事件后清理缓冲。Ready 表示数据已经可供消费者使用，不等于主机已经调用了异步 API。

Release 表示逻辑上不再使用；最后一次消费者执行完成、异步引用结束后，底层存储才可复用。后台不能因看到 Release 指令就提前归还额度。

滚动执行器持续处理完成事件、归还额度并清理结束任务，不等到 Fence 才回收。遇到显式 Fence 时不开放其后的任务，继续推进 Fence 之前尚未完成的计算及其必需准备，待它们和已提交的后台工作结束后再通过边界，并保留后续仍需使用的值；Fence 不能被用成“等待后台一直补到水位”。等待额度时不持有会阻塞完成处理的锁，也不能堵住唯一负责推进消费者或回收任务的 worker。

### 6.4 调度循环示意

```text
on 前台请求、锚点完成、资源回收:
    收集完成事件，发布 Ready，归还真正可复用的额度
    更新对应设备的执行进度，开放 after 已完成的任务，将 start_by 已到的任务提升
    如有前台请求，关闭与该请求冲突的机会性 GPU/传输提交
    优先推进必需明文，回收已完成最后使用的对象
    在合法窗口内选择机会性候选
    若目标设备水位、前台预留、共享 Host/传输额度及后端并发预算均满足:
        调度线程取得所需额度，标记任务已开始
        仅提交一个完整 Encode 或已验证的小 batch
    否则等待进度/回收通知，不阻塞负责释放资源的执行路径
```

当前生产 API 的 `encode_plaintext` 要求 Host 输出。不能仅改变调度器队列就获得 GPU 编码路径，也不能将固定参数的实验 kernel 直接当成通用实现。

当前上传的目标计算流等待还保护异步分配和内存复用顺序。改进重叠时应分别表达“目标缓冲可写”和“结果可读”，不能直接删除等待。只有 trace 中观察到实际重叠，才能报告重叠收益。

### 7.2 必须做的工程修改

**编译器：** 在 Dist dialect 定义准备操作及 verifier；在后期 streaming pass 中改写匹配的 Encode/Transfer、调用时间线分析并生成锚点。`RuntimePlanUtils` 目前只为 CKKS 和 Transfer 结果注册 ValueId，需要接受准备结果；初始化判定、bundle 导出、Release/reuse 和内存估算都要认识该操作。定稿调度后不再运行可能跨生命周期边界合并或移动准备任务的 CSE。

**Runtime：** 保留旧 V3 的按批执行路径，新计划采用持续运行的 worker 和有界提交队列，按滚动窗口注册准备任务和 Pending 结果。当前 `execute_device_parallel_phases/run_parallel_batch` 会为 Fence 区间构造队列、创建线程、join 并清理，不能只删掉 Fence 就得到持续执行器。需要将这些队列的补充和完成清理改为增量方式，同时限制前台计算、通信和准备的在途资源；已有计算/通信任务的执行函数继续复用。

添加一个拥有任务状态的小调度器，接收完成点通知、管理每卡水位和共享预算、分派 CPU/GPU 工作；沿用现有值存储、引用计数和 worker 失败通知。当前 `ValueStore::Pending` 主要对应通信组，需增加准备任务来源，不能假装 GPU Encode 是已有通信句柄。消费者请求尚未开始的准备时负责提升任务，然后由独立准备执行路径推进，不能让等待者同时成为唯一准备执行者。

CPU Encode 和 Host Boot 继续共用串行 CPU worker 时，只分派依赖已齐全的 Host 计算；不能让它占住 worker 等待一份还需要同一 worker 编码的明文。为每张卡复制一个不受约束的 CPU worker 会破坏共享 encoder 和 Host 预算，不作为自然扩展方式。

**API：** 保留现有 Host `encode_plaintext` 和通信接口，增加一个面向目标设备的异步完整 Encode 入口，例如 `encode_plaintext_device_async(desc, slots, stream)`。返回现有 Device Value 及 Ready 事件，保留输入、pinned 和工作区直至完成。CPU 路径由 runtime 组合原 Host Encode 和上传，不让 API 自己决定 CPU/GPU 比例或水位。API 另外提供必要的支持范围、工作区大小和完成状态查询，供准入及锚点推进使用，不暴露通用调度框架。

有一个必须随独立 stream 一起修改的具体点：当前 `ReadyEvent::record` 记录 `gpu_execution_stream()`，`wait_on_execution_stream` 在相同生产线程/设备时可以跳过等待。新增同线程不同 stream 后，这一判断不再足够，必须记录或核对实际生产 stream，并在跨 stream 使用时插入等待。线程相同不能证明两个操作已经有序。

进度锚点只需要记录被 `after/start_by` 引用的前台完成点，可复用已有完成事件或增加轻量进度事件，不给每个算子增加定时器。主机入队进度与设备完成进度分别处理。已有 `collect_completed`、`retain_in_flight`、`drain` 应覆盖准备任务；正常执行持续查询完成和回收，drain 只用于显式整体边界与收尾。

### 7.3 计划格式与兼容性

建议采用显式的新计划版本，例如 V4，表达可以由 CPU 或 GPU 实现的明文准备结果。保留 V1/V2/V3 的既有语义和执行路径；旧执行器必须拒绝不认识的新准备语义，不能忽略字段后继续执行。

新版本增加一个对应 `dist.prepare_plain` 的 `PreparePlaintext` 指令。相关 reader、writer、二进制 I/O、Verifier、打印、能力检查和计划导出同步更新。其余算子格式保持原义；不通过给所有 Compute 指令附加准备字段来实现。

编译器与 runtime 使用稳定标识关联准备任务、消费依赖和实际测量。暂时不增加独立的 ForwardNTT/InverseNTT IR；完整 Encode 的成本、内存和完成依赖已足够支持本阶段调度。

### 7.4 分阶段交付

| 阶段 | 实现内容 | 完成标准 |
| --- | --- | --- |
| A：能力和成本基线 | 明确 CPU/GPU 支持的参数范围，统一计时口径，测量工作区及并发干扰 | 每条支持路径通过数值与元信息验证；成本表注明硬件和版本 |
| B：滚动执行基础 | 固定后端和窗口，持续 worker、每卡额度与完成回收；限制前台/通信/准备的在途资源 | 无周期全局 Fence 时仍可推进和回收，单卡与双卡依赖图通过；旧计划回归通过 |
| C：GPU 准备与让路 | GPU 完整 Encode、每卡独立 stream、每卡一个在途准备、请求让路和必需任务提升 | 实测让路延迟与前台干扰；GPU0 忙时 GPU1 仍能独立准备 |
| D：编译器混合规划 | 加入准备成本模拟、分阶段后端分配和最早/最晚窗口，导出可调整范围 | 静态混合方案可解释；模拟预测与 trace 可逐项比较 |
| E：受约束的运行时调整 | 按每卡完成点推进窗口，在任务未启动时择机改选后端，共享资源上优先处理必需准备 | 调整不突破容量和依赖边界；故意制造设备进度差异仍无死锁或错误 |
| F：多卡完整评估 | 扩大双卡到四卡，测量共享 CPU/Host/链路竞争，接入实际消费者的模型计划 | 报告端到端收益、内存峰值、等待及多卡竞争，不以独立吞吐替代 |

实现时按独立功能提交和推送；涉及子模块时先提交对应子模块，再更新父仓库引用。测试可使用本机及 `ssh 188Server`，以实际可达设备和已记录硬件配置为准。本文本身只交付设计，不启动上述实现。

### 7.5 保持简洁：首版明确不做什么

首版不引入通用任务图执行框架、多种 Fence、独立 NTT IR、硬实时期限、每明文墙钟定时器、运行中后端迁移、CPU/GPU 双份抢跑、任意淘汰重编码、自动 OOM 重试、遗传/MILP 搜索或在线重新 placement。低水位滞回、细粒度暂停和跨 Fence 预取均以测量发现的瓶颈为前提。

必要的检查集中在计划加载时：类型、后端支持、锚点范围和依赖合法性。运行中只做本来就必须执行的容量准入、Ready 等待和完成回收。不支持的后端、错误计划或执行失败直接报错，不静默退回 eager、换另一个后端重跑或降低数值要求。合法候选之间的预先选择属于调度策略，不是错误兜底。

独立 stream、生命周期和容量检查是异步执行的正确性要求；复杂恢复机制和通用扩展框架才是本阶段应避免的额外设计。先用固定后端和窗口跑通，之后每增加一项灵活性，都用消融说明它确实改善性能。

### 7.6 多 GPU：共用语义，区分每卡资源和共享资源

**现有基础不是单 GPU 限定。** 当前 V3 限制为单 rank，但一个 rank 可以管理多张 GPU：计划已有 `Place(kind, rank, index)` 和设备数量，runtime 为每张 GPU 分派工作，GPU API 创建各设备上下文并支持设备间传输。已有[验证记录](poseidon-plaintext-prefetch-validation.zh-CN.md)覆盖四卡 MLP。本文的 Waterline 尚未在单卡或多卡实现，不能将这些既有结果当成新机制的验证。

多卡沿用同一个 `dist.prepare_plain`：其目标设备已经确定，CPU 路径编码后上传到该卡，GPU 路径在该卡完整编码。每张卡拥有自己的水位、前台进度和 Ready 事件。单卡是设备数为 1 的特例，不需要新增多卡专用指令或改动 `mulcp` 等数学算子的语义。首版不增加“在空闲 GPU 上编码，再转发给另一张 GPU”的第三条路径。

| 按设备独立维护 | 同一进程统一协调 |
| --- | --- |
| 显存水位、前台预留、驻留明文、Encode 工作区 | CPU Encode 能力、Host 原始数据与编码结果预算、pinned 预算 |
| 前台完成点、候选窗口、计算/Encode stream、Ready 事件 | 共享传输链路的占用及与前台通信的竞争 |
| 本卡任务的在途限制和回收 | 必需准备优先级、跨设备依赖及共享对象引用 |

因此 GPU0 显存满或忙碌时，GPU1 仍可准备；只有实际争用的 CPU、Host 容量或链路受限时，才限制相关任务。仍用一个拥有额度账本的小调度器和已有每卡 worker，无需每卡复制一套独立运行时。CPU encoder 首版保持串行；若以后扩成实例池，CPU 并发额度也仍由全进程共享。

多卡需要额外处理的主要是以下三个问题：

1. **共享吞吐。** 多张卡不会各自获得完整的 CPU 编码能力和 PCIe 带宽。模拟器同时回放各卡准备、H2D 和前台设备间通信；同一链路上的竞争使用测得的并发成本或保守带宽分配。共享队列优先处理已到期或已被请求的准备，机会性任务按预计需要时间选择，同优先级可轮转。不同设备的本地完成序号不能直接比较大小。
2. **依赖和前进。** GPU1 等待 GPU0 的结果时看起来空闲，但它仍需为接收缓冲和即将执行的消费者保留资源。不能让远期 Encode 占满这些资源，或用全设备 Fence 等待 GPU0。保留现有通信依赖和顺序，以各卡真实完成事件推进窗口；某卡等待额度不能阻塞其他卡的完成处理。第 7.2 节的持续 worker、有限提交和回收也是多卡滚动执行的基础。
3. **对象和事件归属。** 各卡的明文副本分别计费、分别发布 Ready。相同 payload 的现有共享 Host Encode 加多目标上传可以保留，不强制改成每卡重复 CPU 编码；若共享一个 Host 编码结果，必须等所有上传真正完成后再释放它。首版不另加跨 Prepare 的全局缓存去重优化。GPU Encode 的上下文、参数表、工作区和实际生产 stream 必须属于正确设备，单卡原型正确不足以证明多卡并发安全。

实现顺序可以先单卡测成本，但滚动执行基础阶段就要加入双卡有真实通信依赖的测试，验证一张卡变慢、另一张卡推进以及共享 CPU 排队的情况，再扩大到四卡。这里增加的是资源竞争建模和执行器协调，不是一套新的编译器语义。多进程或跨机器还涉及远端进度、Host 预算和通信协调，不属于本计划已承诺的支持范围。

## 8. 正确性与验证计划

### 8.1 必须保持的性质

1. **数值和元信息正确。** 两条后端输出具有一致的编码语义、level、scale、RNS 基、NTT 布局和槽含义。完整 GPU FFT 可能存在与 CPU 不同的舍入；分别报告是否逐系数一致，以及端到端 CKKS 误差是否符合既定容差，不能以微基准的局部一致性代替通用验证。
2. **先就绪，后使用。** 消费者必须依赖目标设备上的 Ready 事件；模拟时间到达不能替代依赖。
3. **先预留，后分配。** 所有并发任务共享一致的额度账本；Release 后但尚未完成的对象仍计费。
4. **保持前进。** 等待容量不会阻塞消费者、完成处理或回收；必需明文可取得预留容量，机会性任务不能使其饥饿。
5. **失败可收敛。** 后端失败、读取失败或预算不足时，唤醒所有依赖方，等待已提交工作安全结束并释放资源，不留下永久 Pending 值。

测试覆盖启动未填满、恰好达到水位、并发准入、水位降低、重复消费者、共享原始数据但参数不同、上传未完成即请求、提前 Release、请求在编码期间到达、CPU/复制延迟注入、后端不支持、分配失败、滚动窗口推进和显式 Fence。多卡用例还要覆盖单卡额度耗尽而另一卡继续、共享 Host 结果的多目标上传、设备间通信与预取竞争，以及长期无 Fence 时的内存稳定性。CPU encoder 的线程安全未经验证时，继续使用串行 CPU worker 或独立实例，不能直接共享后并发调用。

### 8.2 性能对照与消融

| 对照或消融 | 验证的问题 |
| --- | --- |
| 全量预编码并驻留，仅在装得下时 | 理想就绪条件下的前台基线与内存代价 |
| 现有分批 CPU Encode，无预取/固定字节预取 | 相对当前系统的实际收益 |
| CPU-only 与 GPU-only，使用相同容量和窗口 | 混合后端是否必要 |
| 固定比例与编译器分阶段比例 | 模拟驱动后端选择的贡献 |
| 静态计划与允许 runtime 修正 | 对预测误差和负载变化的适应能力 |
| 不同 waterline、窗口、batch、提交深度 | 内存、等待和让路延迟的取舍 |
| 现有批次 Fence 与持续滚动执行 | 取消周期整体等待、按完成事件回收的收益和开销 |
| 单卡、双卡与四卡，包含不均衡进度 | 共享 CPU/Host/链路竞争与每卡独立推进的效果 |

首先运行消费者真正读取所准备明文的小图，再扩大到 MLP、模型局部和完整模型。此前独立前台算子与 Encode 并发的实验适合建立干扰成本，不等价于这类供需闭环测试。完整模型的编译成功、实际装入显存和数值完成分别报告。

主指标包括冷启动到首个结果时间、稳态端到端耗时、吞吐和前台延迟分布。辅助指标包括明文等待时间、期限错失、CPU/GPU 实际分配比例、H2D 字节与时间、重复编码、前台算子减速、后台让路延迟、调度开销，以及 GPU/Host/pinned 的活跃峰值与池保留量。单请求实验不冒充服务请求的 P99 测量。

测试既包含有空闲间隙的负载，也包含 GPU 持续忙、CPU 供应不足和预测明显失准的情况。扫描 waterline 时保持其他预算和工作负载一致；初始填充不得从冷启动指标中隐藏。使用 CUDA events 与 trace 核对跨 stream 重叠，并记录温度、时钟、重复运行与采样方法。

论文中的每项收益都应对应完整对照实验。实现完成前，这些内容是待检验的设计假设，不写成实验结论。
