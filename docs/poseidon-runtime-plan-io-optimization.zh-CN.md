# Poseidon RuntimePlan 生成与读取开销优化方案

2026-10-10。面向 DaCapo 导出器、ckks-runtime 读取器和 Poseidon 执行入口的后续实现方案。

实施状态：阶段 A–C 已实现，采用严格单遍 SAX、逐记录 typed plan 构建、增量 SHA-256、紧凑流式导出、manifest 写流和 staging 发布。代码、测试、完整 V2/V3 元数据测量及四卡 Qwen 导出证据见 [I/O 优化验收记录](../test-results/runtime-plan-io-188-20261010/README.md)。元数据加载峰值已低于 16 GiB；180 秒时间目标仍需继续优化。阶段 D 的 bundle pack 已实现并支持显式预算下的 raw 内存驻留，见[pack 验收记录](../test-results/runtime-bundle-pack-188-20261011/README.md)；压缩入口和阶段 E 的二进制容器继续按下述条件推进。

原始四卡 JSON 的 31.03 MB/s 是端到端加载速度：读取 1.82 秒，解析与 typed plan 构建 213.89 秒，增量 SHA-256 55.88 秒，总计 271.59 秒。CPU 解析和对象分配是主要瓶颈；该数字不表示磁盘带宽。合并权重文件不会消除 JSON 的解析时间，后续应减少逐记录临时 DOM、字段查找与分配，或采用阶段 E 的二进制计划。

pack 将 784,750 个 `.bin` 合并为一个 `data.bin`，以 content ID、offset 和长度索引。默认保持一个文件句柄按范围读取；显式设置 `BundleReadOptions.resident_byte_limit` 后顺序预载整个 raw pack，后续从不可变内存范围取数据。新导出默认 pack，旧布局可通过 `--runtime-plan-bundle-format=files` 保留；已有产物可用合并工具转换，无需重跑编译器。存储协议、兼容条件和工具用法见[明文数据包存储 V2](../third_party/ckks-runtime/docs/runtime-plan/v2/plaintext-bundle.md)。

阶段 E 已完成独立二进制小实验，尚未切换生产入口。188Server 上约 40 万条 V3 MLP 指令及描述符的加载中位数由 4.031 秒降至 0.398 秒，计入同一 PlanVerifier 后为 4.502 秒与 0.897 秒；真实 784,750 项 manifest 由 3.460 秒降至 0.825 秒。三次交替测量保留元数据 SHA-256，不读取权重 blob。计划样本是独立 MLP 计算图的复制，不能将约 10.1 倍加载倍率外推为完整 Qwen 或推理加速。编码、正确性与工程化边界见[二进制实验记录](../test-results/runtime-binary-io-20261011/README.md)。

随后直接转换既有完整 V3 Qwen JSON：11,064,667 个描述符、22,149,239 条指令，8.756 GB 转为 1.470 GB，全部字段读回一致。188Server 单次成功运行的 JSON 加载 278.424 秒，二进制独立进程加载 22.147 秒，快 12.6 倍；计入同一 PlanVerifier 为 312.003 秒与 54.427 秒，快 5.7 倍。纯解析与构建为 220.622 秒与 12.362 秒；加载峰值 RSS 5.689 / 5.507 GiB，含 Verifier 均约 8.734 GiB。没有读取或校验权重载荷，生产入口尚未切换，见[完整 Qwen 二进制实验](../test-results/runtime-binary-qwen-188-20261011/README.md)。

按用户要求，后续二进制实验关闭整文件 SHA；优化生产 PlanVerifier 的状态索引、错误文字和模数前缀和，并在实验入口支持多线程构建现有 RuntimePlan。完整文件无需重新转换，流式无 SHA 加载 13.210 秒，新 Verifier 6.977 秒；8 线程游标读取两次为 5.841–5.965 秒，加载加校验 13.395–15.240 秒，完整单线程/8 线程结果逐字段一致。4 线程总耗时 14.166–14.219 秒更稳定。扫描和数组初始化仍串行，原 JSON reader 默认摘要行为及生产格式入口未切换，见[无 SHA 与多线程验收](../test-results/runtime-binary-parallel-188-20261011/README.md)。

Poseidon CPU/GPU MLP 执行入口可设置 `POSEIDON_RUNTIME_BUNDLE_RESIDENT_BYTES=17179869184`，提供 16 GiB raw 驻留上限；未设置或为零时按文件 offset 读取。预算不包含计划、索引、解码 slot 或 RNS 对象；独立 rank 进程各占一份。在 V3 中 raw pack 持续驻留，Encode/Fence 仍控制解码和 RNS 生命周期；V1/V2 计划完成 eager load 后释放 raw 缓冲并保留本地 slot。超预算或旧 V1 bundle 请求驻留直接报错。

当前 Qwen 已达到千万级指令规模。应先消除 JSON 解析中的平方级扫描，再同时改造生成端和读取端，减少完整对象树、大字符串、重复遍历和小文件访问。近期保留现有 JSON 语义，采用紧凑、流式的读写方式；压缩用于归档与传输。分块二进制格式作为后续选项，根据修复后的启动时间和内存预算决定是否实施。

这里的“流式读取”指逐步构建执行计划，首版仍在完整读取和校验后执行。它与 V3 在计算途中读取、编码明文的功能分别控制计划元数据和权重对象的开销，两者需要配合。

临时程序使用上述两遍解析，对完整四卡文件调用原有计划转换和 SHA-256 实现，结果如下。DOM 是 JSON 的完整内存对象树。

| 阶段或指标 | 结果 |
| --- | ---: |
| 文件读取与字符串构建 | 49.59 秒 |
| SAX 检查和 DOM 解析 | 203.96 秒 |
| DOM 转为 RuntimePlan | 101.91 秒 |

### 存储和序列化

四卡计划在同一 DOM 上进行内存内序列化，未计写盘：

| 表示 | 大小 | 序列化时间 |
| --- | ---: | ---: |
| 缩进 JSON | 8.428 GB | 93.73 秒 |
| 紧凑 JSON | 4.892 GB | 40.19 秒 |

这些结果说明磁盘和网络开销可以大幅下降。但解压后继续构造相同 DOM，会继续承担对象分配和内存放大；MessagePack 保留字段名和字符串 ID，也无法单独解决执行计划的内存布局问题。

## 与现有改动的关系

性能基线使用 ckks-runtime `641e2ee0567f4f531da6146b7817295bfeeee092`。编写本方案时读取的代码为 Poseidon `71dc4fe108b413914c7f62d0f213a1a69555a28d`、ckks-runtime `63e1d68f25154a20d8b350a1ff06af4649538df0`、DaCapo `b60fb1d27eadded0bc352d8186851b1caeac39a2`，工作区还有并行修改。

当前 [runtime.hpp](../third_party/ckks-runtime/runtime/runtime.hpp) 已建立 `descriptors_` 哈希索引，避免基线中每次 `desc(id)` 线性扫描全部值；也已有 V3 Fence、按需读取 bundle 和分批任务构建路径。本方案复用这些工作，不再次规划同一功能，也不把 V2 测量当作新 V3 的性能。

当前 JSON 回调扫描、全文本加载、DOM 转换及导出端 `plan.dump(2)` 路径仍在。明文调度的背景和内存语义见[明文预取方案](poseidon-plaintext-prefetch-implementation-plan.zh-CN.md)；该文档开头的实现状态早于上述代码快照，实施时以对应提交和测试结果为准。

## 优化后的完整路径

```text
完成物理元数据与内存调度的 IR
  → 复用 ID 和阶段布局
  → 按指令写紧凑 JSON，同时写去重后的常量数据
  → 写 manifest 并完成内容哈希
  → 发布完整产物，可选压缩用于分发
  → 分块读取或解压，增量哈希，SAX 构建 typed plan
  → 完整结构和语义校验，建立一次性索引
  → 根据 V3 调度按需读取、编码、上传明文
  → 按批构建任务并执行
```

首轮改造保持算子、ValueId、TransferId、ordinal、阶段内顺序和 Release/reuse/Fence 语义。降低序列化开销不应重新触发模型跟踪、boot 放置或明文调度。预取、显存预算和 CKKS 数值验证继续由对应执行方案负责。

## 读取端方案

### 消除回调中的父数组扫描

第一步只解决解析算法，不先更改磁盘格式。可以在当前版本上审查并修复回调的容器扫描，也可以使用公开 SAX 接口构建严格读取器。两遍解析对照适合验证根因，若作为过渡实现，需要明确其重复扫描成本；目标实现采用单遍 SAX。

保留重复键、未知字段、必需字段、类型、整数范围、规范十进制 ID、有限数值和 BOM 等现有约束。固定 schema 的对象可用字段位图跟踪已见字段；按解码后的键识别重复，不能让转义写法绕过检查。不要为加速直接移除重复字段检查，或依赖普通 DOM 对重复键的覆盖行为。

同时检查 plan、OperatorSpec 和 bundle manifest 的共用解析入口。错误应带文件、字节位置或 ordinal，避免在每个成功读取的标量上反复构造长错误路径字符串。

### 直接构建执行计划

reader 从有界输入缓冲区获取事件，在完成一个 ValueDesc 或指令时直接写入 typed 容器，完成后复用临时状态。内存目标从“文本加 DOM 加 plan”降为“plan 加索引加有界缓冲区”。

现有 JSON 不保证根字段顺序，且 Qwen 文件以 execution 开头。新 reader 必须继续接受任意合法字段顺序：可先保存 typed 指令，等所有描述符、目标和版本信息齐全后统一校验。不能要求先看到 values 或 format_version，也不能在文件尚未结束时提交 GPU 操作。尾部截断、非法版本或哈希不符都必须在执行前报错。

过渡阶段可先对 DOM 中已知长度的 values、各阶段指令和输入列表调用 `reserve`。单遍 SAX 不知道数组长度时使用分段容器或正常几何扩容；不要每插入一个元素就精确 reserve，也不要为了得到长度重新做一次昂贵 DOM 解析。若之后增加 counts 元数据，仍需核对实际数量并约束分配上限。

读取 JSON 不等于执行时也按文件块释放计划。跨批值、引用计数、最终输出和全局校验目前仍需完整元数据；让计划本身按块驻留属于后续协议与执行器改造。

### 合并读取与哈希遍历

当前先完整读取，再解析，最后对整个字符串计算 SHA-256。新增增量哈希接口，在读取缓冲区进入解析器前更新摘要，避免额外遍历和长期保留全文本。对于解析器预读的数据，每个文件字节只进入摘要一次，不能因重试或缓冲复用重复计入。

增量处理只减少遍历和峰值，不自动消除 SHA-256 的 CPU 成本。本例现有实现用了 69.71 秒，需单独比较大块输入下的吞吐量；必要时评估已有依赖或经过验证的硬件加速实现，保持摘要逐字节一致和离线可构建。不要通过关闭摘要验证获得性能结果。

读取压缩文件时，明确区分压缩文件的传输摘要与解压后 JSON 的 `source_sha256`。原始 JSON 的空白和末尾换行都属于源字节；紧凑输出会产生新摘要，不能沿用旧摘要。解压、哈希和解析可先在单线程有界管线中完成，实际需要时再加入有背压的生产者线程。

### 控制长期保存的元数据

保留已经加入的描述符索引。若进一步改为按连续内部编号访问，先建立并验证 ValueId 到内部编号的映射；不能假设外部 uint64 ID 连续或较小。

`reserve` 完成后仍应统计结构体数组、嵌套输入 vector、context 字符串、使用次数表、Verifier 集合、任务闭包和 allocator 保留量。可逐项评估共享 context 字符串、连续 operand 池、轻量 Release 记录，以及按批构建任务。不要直接把 C++ variant 的内存布局写入文件。

对相同不可变计划的多次运行，可由调用方显式持有已加载、已校验的计划与索引。校验复用必须绑定计划内容、OperatorSpec 摘要和校验规则版本；本机 rank、设备数与资源匹配仍在绑定时检查。避免用路径或文件名作为有效性依据，也不引入无容量约束的全局缓存。

## 生成端方案

### 先消除缩进和整份输出字符串

[EmitRuntimePlan.cpp](../third_party/ckks-runtime/third_party/dacapo/lib/Dialect/CKKS/Transforms/EmitRuntimePlan.cpp) 当前构造完整 JSON 对象，再调用 `dump(2)` 得到整份字符串。首个兼容性改动是以紧凑形式写入有缓冲的输出流，默认不生成缩进空白；可读格式作为显式诊断选项。

直接将现有 DOM 写流，只消除了巨大的输出字符串，DOM 仍存在。下一步将 builder 改为逐条发出记录：保持小型 ID 索引与布局数据，每次只构造一条记录或一个有界块，序列化后释放。输出缓冲区按块提交，不能每个字段、每条指令都 flush。

字符串转义、浮点格式和 JSON 合法性继续复用可靠的序列化实现。固定字段顺序、遍历顺序和浮点输出规则，使同一输入与编译选项产生确定的字节序列。ID、ordinal 和分阶段顺序来自现有公共布局，不能为每个导出格式独立重建一套编号规则。

### 在流式导出中完成 bundle 引用

导出 Encode 时，继续复用现有 DenseElementsAttr 缓存和内容哈希去重，只对首次遇到的常量进行转换、写出和登记。初始化与 execution 中的 Encode 都要处理，不能将 V3 的在线 Encode 移回初始化。

可以在指令数组写完后生成 bundle manifest，取得摘要，再将 `plaintext_bundle` 作为 plan 的后续根字段写出。这样无需为提前得到 manifest 哈希而保存完整 plan DOM，也无需重新遍历和转换全部常量。现有 reader 接受根字段任意顺序，新 SAX reader 也须保持这一性质。

manifest 同样逐项写入并增量哈希。保留内容去重需要的哈希、长度和属性索引，但不保存已写出的原始浮点数组副本。把首次创建目录移到 writer 初始化；多进程写同一产物不在默认写入模式中隐式支持。

### 分解导出阶段并复用已有产物

给 EmitRuntimePlan 分开计时：布局与编号、常量转换、常量哈希、常量写入、manifest、指令序列化和 plan 写入。记录各项字节数、唯一 blob 数、重复命中数，以及进入导出阶段后的 RSS 变化。

只比较格式时复用同一已调度 IR 或已有计划，不重新生成权重和跟踪模型。完整编译的 parser、调度、JSON 导出和诊断 MLIR 输出分别报告。诊断文本 MLIR 可在不需要时关闭，不能把减少这部分时间计作 JSON 优化收益。

发布采用同一文件系统中的临时文件或 staging 目录。完成所有文件、摘要、关闭与错误检查后再发布最终 manifest/入口；失败时不留下看似完整的最终文件。要求断电持久性时另计 fsync 成本。恢复或复用既有 bundle 时验证内容引用，不能只凭文件存在就跳过检查。

## 压缩和 bundle 文件组织

近期支持 JSON 与其无损压缩包装，两者解压后的 schema 相同。先用外部分发工具压缩并测量解压成本；需要 runtime 直接读取压缩文件时，再增加明确的格式入口和可离线构建的依赖。未知格式或损坏数据直接报错，不静默切换读取方式。

压缩后的计划可以不落地为多 GB 文本，而是直接送入 SAX reader。设置输入缓冲、解压缓冲和输出队列预算，报告解压吞吐量。压缩比不能替代启动测量，也不能把字节数下降比例当作加载速度提升比例。

约 78.5 万个小文件的路径解析、open/close 和零散读取值得独立测量。后续建议新增 bundle 存储版本，以少量 pack 文件和索引替代逐 blob 文件：

- 索引记录 content hash、pack 编号、64 位 offset、原始长度，以及需要时的压缩长度和编码类型。
- writer 追加数据，完成索引后发布；reader 校验边界，通过 `pread` 或受控映射读取所需范围，并按原始内容哈希验证。
- 需要压缩时按 blob 或有界块独立压缩，保留随机访问能力。整个 14.70 GB bundle 做成单个顺序压缩流，会损害 V3 按需读取。
- 根据实际 Encode 访问顺序改善数据局部性，同时保留内容去重。比较重复访问、读取放大和缓存命中，不仅比较打包后文件个数。

计划语义版本、bundle 存储版本和压缩包装分别定义。V3 Fence 不自动等于二进制计划或 pack 格式。新 reader 可显式支持旧 bundle；遇到不支持的新版本应明确失败。原始数据缓存继续服从明文按需加载方案的字节预算，不将其扩大成全量 RNS 缓存。

## 何时采用分块二进制计划

完成算法修复与流式 JSON 后，如果启动时间、typed plan 大小或多进程重复加载仍超出预算，再引入独立的二进制容器。格式需要明确版本、字节序、节目录、长度、摘要和必需特性；使用整数 ID、枚举操作码、公共字符串表和连续 operand 区。

优先按有界记录块保存 values 和各阶段指令。块边界只是存储边界，不自动成为 Fence，也不允许重排计算。跨块引用和 Release/reuse 的校验仍完整执行。支持跳读某些 rank 或按批驻留之前，要定义全局校验所需的摘要和依赖元数据；仅将文件分块并不能自动省去全局计划。

| 选择 | 能改善的部分 | 仍需解决的部分 |
| --- | --- | --- |
| 紧凑 JSON 加 SAX | 缩进、全文本、DOM、转换中的重复对象 | typed plan 和运行准备内存 |
| JSON 加 zstd | 存储与传输 | 解压、解析和索引成本 |
| MessagePack 或 CBOR | 文本标记和部分编码成本 | 重复字段名、DOM、typed 布局 |
| 有 schema 的分块二进制 | 重复元数据、解析、可索引访问 | 格式演进、边界验证、兼容性与调试工具 |

不建议把现有 5–8 GB 单 JSON 文件直接交给 simdjson 替换：其文档对单文档约 4 GB 的限制需要通过布局改造解决。[simdjson 官方说明](https://simdjson.org/api/4.6.4/md_doc_2basics.html)。使用 FlatBuffers 等方案前也需核对偏移和块大小限制；默认 32 位 offset 不是任意大单文件的承诺。[FlatBuffers 格式说明](https://flatbuffers.dev/internals/)。近期 SAX 方案可以复用现有库的[公开接口](https://json.nlohmann.me/api/basic_json/sax_parse/)，不必先引入新的重型依赖。

## 实施顺序和代码范围

| 阶段 | 主要工作 | 主要位置 | 交付条件 |
| --- | --- | --- | --- |
| A | 消除回调平方级扫描；保留严格检查；已知数组 reserve | ckks-runtime 的 json_utils、json_plan_reader、相关 JSON 测试 | 大数组接近线性增长，V1/V2/V3 接受和拒绝行为正确 |
| B | 紧凑写流、分解导出计时，去掉整份 planBytes | DaCapo 的 EmitRuntimePlan、runtime-plan 测试 | 同一计划元数据与指令逐项一致，输出摘要正确 |
| C | SAX 直接构建 typed plan、增量哈希；逐记录导出和 manifest 写流 | 上述 reader/writer、SHA-256、bundle loader | 全量 Qwen 元数据加载与导出均有内存和时间报告 |
| D | 压缩入口、bundle pack、按需范围读取 | bundle 协议、writer/loader、Poseidon 资源绑定 | 摘要、随机读取、缓存预算和 V3 行为通过验证 |
| E | 按预算决定二进制容器和更紧凑的执行表示 | plan schema、reader/writer、Verifier、runtime | 相比阶段 C 有明确收益，兼容规则和调试导出完整 |

阶段 A 和 B 可以分别落地，阶段 C 同时消除读写两侧的完整 DOM。D 的 pack 设计不依赖 E；采用二进制指令也不代替明文调度。实现涉及的子模块按 DaCapo、ckks-runtime、Poseidon 的依赖关系分别提交和更新，避免把临时基准修改混进功能提交。

## 验收与性能预算

首先验收正确性，再判断速度。新旧读取结果逐项比较 target、values、指令与属性、输入输出、Release/reuse/Fence 和 bundle 引用。继续使用 PlanVerifier 检查定义、使用、释放、物理元数据和设备约束。小型真实 CPU/GPU CKKS 用例验证执行结果；全量 Qwen 的序列化通过不代表完整 FHE 执行通过。

错误测试至少覆盖重复键及其转义形式、未知或缺失字段、错误版本、非法 ID、截断文件、尾部垃圾、哈希不符、错误 blob 长度、pack 越界和压缩损坏。加入任意根字段顺序、V3 在线 Encode/Fence、跨块引用及短读情况；新 reader 不得因性能优化接受原来应拒绝的输入。

性能测量固定输入哈希、源码提交、编译选项、线程数和缓存条件。片段测试每档至少三次，报告中位数与范围；完整计划至少一次受限运行，资源允许时重复。冷热读取分别定义，不在共享服务器全局清页缓存。大产物放在指定数据目录，临时目录只保存小型工具和结果。

| 项目 | 必须记录 | 首轮工程目标，尚非实测承诺 |
| --- | --- | --- |
| 解析增长率 | 相同记录分布的 10/20/40/80 万条耗时 | 数据翻倍时耗时通常不超过 2.5 倍，异常需定位 |
| 完整四卡元数据加载 | 读取、解压、解析/构建、哈希、销毁、峰值 RSS | 阶段 C 后，上述读取至哈希部分争取低于 180 秒、峰值低于 16 GiB |
| 校验与运行准备 | Verifier、索引、使用次数和任务构建时间及 RSS | 独立设预算，不将其排除后宣称总启动达标 |
| 生成端 | 各导出子阶段耗时、逻辑字节、写入字节和阶段 RSS | 消除完整 plan DOM 与 planBytes；临时记录/输出缓冲区按配置有界 |
| bundle | open 次数、读取字节、随机读取延迟、哈希、缓存占用 | pack 显著降低文件访问次数，V3 按需读取不退化为全量解压 |
| 重复运行 | 每轮 RSS、重复校验、重复读 blob 和旧任务保留量 | 同一计划多次运行无持续内存增长 |

180 秒和 16 GiB 是基于本例规模提出的初始预算，需要用相同服务器复测确认。16 GiB 只覆盖计划元数据加载，不包含完整运行资源；如果 typed plan、Verifier 或任务表示成为主因，应先缩减这些结构，再决定二进制格式。相比 52.26 GiB 的临时对照只比较相同测量范围，不能将其标成相对原版完整运行的收益。

生成端以进入导出阶段的 RSS 为参照，并另外报告整个编译进程峰值；allocator 保留量和 IR 占用会影响差值。直接写流的吞吐量、压缩吞吐量和实际磁盘写入分别测量，不用单独 `dump` 的速度替代完整导出结论。
