# Poseidon 内存释放和原位计算实施方案

这次先做两件事：**不用的数据及时释放；能安全覆盖输入的计算，直接使用输入的那块内存。**

另外在编译器里增加峰值内存估算，查看任务分到不同设备、加入释放和原位之后，各处最多需要保存多少数据。通过编译器选项生成报告，不增加 Verifier 的职责。现有 Python 脚本只是验证计算方法的临时参考；编译器内的正式功能尚待实现。

预取暂时不做。权重什么时候上传，继续沿用现在的安排。这次也不加入为预取准备的 `wait=true`、双权重窗口和队列等待机制。

## 1 做完之后是什么样

现在，很多中间结果会一直保留到运行结束，GPU API 还会继续持有已经用完的对象。要先解决这个问题。

例如，原来的计划是：

```text
a = Negate(x)
b = AddCP(a, w)
return b
```

加入释放后，可以变成：

```text
a = Negate(x)
Release(x)          // 后面不用 x 了
b = AddCP(a, w)
Release(a)
Release(w)
return b            // 返回结果保留
```

如果 a 满足原位条件，还可以变成：

```text
a = Negate(x)
Release(x)
b = AddCP(a, w), reuse_input=0
Release(w)
return b
```

这里 b 直接使用 a 的内存，a 这个旧名字以后不能再用，也不需要再写 `Release(a)`。如果后面还有同样的操作，可以连续覆盖三次、四次，不必每一步都新建一份密文。

这次支持 CPU 的 Negate、Rotate，以及 GPU 的 AddCP、SubCP、Rotate。其他计算继续生成独立结果。GPU SubCP 先通过手写计划测试，不为它增加编译器数学算子。

## 2 释放的关键是等正在使用它的工作结束

`Release(x)` 表示程序后面不再使用 x，不表示 GPU 已经停止读取 x。

例如 CPU 已经提交了 `b = AddCP(a, w)`，随后读到 `Release(w)`，但 GPU 可能还在算。此时直接销毁 w 会出错。

处理办法分成两层：

- **Runtime 管还没提交的工作。** 在执行前统计每个值会被用几次。某个计算或传输成功提交，并且 API 已经接手保存需要的数据后，再减一次。遇到 Release 时，如果还有工作没提交，就先记下“以后可以释放”，继续保留数据。
- **API 管已经提交的工作。** 每次异步计算或传输，保存它会用到的数据和完成事件。事件显示完成后，清掉这些引用。

两边都不再持有数据时，内存自然可以归还。这里用普通计数和已有的 CUDA 事件、通信请求即可。

多线程下不要一遇到 Release 就删除值表中的那一项。其他线程可能还没拿到它。保留表项，只在条件满足时清空里面的数据；计数和清空操作加锁保护。

传输结果如果晚一点才到，也检查同样的条件：已经不需要、也没有尚未提交的使用，就收到后直接清掉，不重新保留到运行结束。

计数要覆盖初始化、执行和收尾三个阶段，初始化结束时不能重新从零开始。一个传输如果被拆成多次发送，就要等这些发送全部成功提交，才能认为它已经用完源数据。计算函数里的临时输入副本也应在减计数前清掉。

最终输出继续交给调用方。外部输入如果调用方还留着，Release 只清掉 Runtime 自己的引用，不会强制销毁调用方的数据。

## 3 GPU API 具体怎么改

主要改 `src/poseidon/runtime_api/poseidon_gpu_api.cpp`。

现在的 `retain_in_flight()` 会把数据放进一个持续保留的列表。把它改成按工作保存：

```text
一次计算或传输：
    它什么时候完成
    完成前需要保留哪些数据和临时缓冲区
```

增加两个简单的清理入口：

- `collect_completed()`：查看哪些工作已经完成，清掉它们保留的数据；不等待尚未完成的工作。
- `drain()`：运行结束时，等所有已经提交的工作结束并清理。

提交工作后、处理 Release 时，以及运行结束时调用这些入口。不必新增后台清理线程。由于这次没有等待式 Release，也不需要建立“每块内存被哪些操作读取”的反向查询表。

还有三处要一起处理：

1. **传输结果交给 Runtime 后，通信状态不要再留一份。** 现在 `posted_outputs()` 会复制结果，`wait()` 又会返回结果。改成每个结果只交付一次；提前交过的，wait 就不再交。两边按原输出位置对应，避免混淆结果。
2. **临时传输缓冲区用完就清掉。** GPU 下载到 Host 时，先用临时数据构造 Host 结果，再清掉临时区；发送端即使没有返回结果，发送结束后也要清理。
3. **收尾要等全部已提交工作。** 不能只等最终输出，因为有些已提交计算不在最终输出的依赖链上。

Runtime 的通信接收代码以及 CPU、GPU、Mock、MPI 的对应接口一起修改，避免一边改成“只返回新结果”，另一边还要求“返回全部结果”。当前 GPU wait 会调用 posted_outputs 并丢弃返回值，这一处也必须调整。

如果提交到一半失败，已经提交的工作仍要保留所需数据。沿用已有报错和通信终止方式，不尝试继续使用可能已被改写的结果。

## 4 原位计算怎么做

先把允许覆盖的条件定得简单一些。被覆盖的输入必须同时满足：

- 来自本次程序内部的计算，不能是调用方传入的数据，也不能是传输生成的副本。
- 它本身不属于最终返回值。
- 在整个计划里，只被本次计算用到一次。传输也算使用；`AddCC(x, x)` 算两次。
- 输入和输出在同一设备，类型、层级、scale 等保持兼容。
- 操作属于本次支持的原位操作，覆盖输入 0。

上一次原位计算的结果可以继续原位计算。最终结果 b 可以覆盖 a 的内存，只要 a 本身不需要作为另一份最终结果保留。

实现上增加明确的 `compute_reuse()` 入口。Runtime 把旧值交进去，API 在原内存上修改，返回给新值。没有 reuse 标记的计算继续使用普通路径。写了 reuse 却做不到时直接报错。

CPU Negate 当前会先复制输入再取负。原位路径省掉这次复制，直接修改输入密文。

GPU AddCP/SubCP 底层已有原位函数。在 `gpu_evaluator.h/.cpp` 增加对应入口，复用普通路径的参数检查，再调用这些函数。不要把同一个对象同时传给普通计算的输入和输出：现有辅助函数在这种情况下会重新分配内存。

原位计算也要等输入准备好，再提交计算，并给新值记录这次计算的完成事件。不能直接沿用旧值“已经准备好”的事件。

是否允许原位由上面的使用规则决定，不用 `shared_ptr::use_count()==1` 来判断。API 为了等待 GPU 完成，也会正常持有同一份数据。

测试时要看实际存储密文的内存是否保持不变，不能只看 C++ 对象地址。连续三次原位计算要使用同一组内存块，也不能先算出一份完整结果再复制回去。

**Rotate 也加入，但允许它使用计算必需的临时空间。** 这里的原位是“最终结果仍放在输入那块内存里”，不要求计算过程中完全不申请临时内存。

CPU 底层已有直接修改密文的旋转实现。把它接到新的原位入口，省掉 Runtime API 中先复制密文、再逐步新建结果的过程。

GPU 的普通 Rotate 现在会新建一份结果。新增 `rotate_inplace()`，直接复用输入密文的存储。旋转会重新排列数据，如果边读边覆盖，可能把后面还要读的数据破坏掉；现有排列 kernel 也明确不支持输入输出使用同一地址。因此需要一个临时多项式缓冲区：先排列密文的第一个分量并写回，再用同一缓冲区排列并保存第二个分量，将原第二分量清零，最后把密钥切换的结果直接累加到原密文中。这样不用另建一份完整的最终结果。

GPU 还有使用预旋转密钥的分支。它先在已有工作区中计算，最后一步可以写入原密文；新增原位入口时要检查这条分支也不会重新分配最终结果。临时空间要保留到 GPU 用完，连续操作可以按同一条执行流的顺序复用，不能让并发操作互相覆盖。

一个 Rotate 有时会被拆成几次小旋转。这些小旋转也应连续使用同一份密文，不能只把最后一步改为原位。补上零旋转、正负旋转和拆成多步的测试，仍然比较实际内存和计算结果。Verifier 沿用前面的简单规则，不因 Rotate 增加一套分析。

**不过，同一输入要旋转出多个结果时，不能直接覆盖它。** 例如：

```text
a = Rotate(x, 1)
b = Rotate(x, 2)
c = Add(x, a)
```

这里 a 和 b 都要从原来的 x 计算，后面还要用 x，所以不能让第一次旋转改掉 x。本次继续保留“被覆盖的输入只有一次使用”的规则。将来若放宽为“允许最后一次使用时覆盖”，还要保证前面异步提交的计算和传输已经读完；这次不顺带增加这部分功能。

## 5 Verifier 只补必要的检查

保留当前已有的类型、算子参数和设备检查。在现有 `runtime/verifier.cpp` 中增加少量逻辑即可，不新建独立分析框架，也不增加一套复杂的内存验证 Pass。

新增检查只处理三类错误：

| 要检查什么 | 例子 |
| --- | --- |
| 已经释放或被原位覆盖的旧值，不能再用或再次释放 | `Release(a)` 后继续用 a；生成 b 覆盖 a 后又使用 a |
| 需要返回的值不能提前释放或覆盖 | 最终要返回 a，却先执行 `Release(a)` |
| 原位计算必须满足上一节的简单条件 | 覆盖外部输入；a 还有另一处使用；给不支持的操作加 reuse |

实现只需先遍历一次计划，统计每个值的使用次数；再按实际执行顺序遍历，记录哪些旧值已经不能用了。定义来源和最终返回值从现有计划直接查。Release 本身不算一次数据使用。

不要求每个中间值都必须显式写 Release。漏写时仍可运行，在结束时统一清理，只是没有提前省内存。编译器是否插对 Release 用几个直接的测试检查，不把“释放得够不够早”变成计划合法性的要求。

具体内存布局能不能原位使用，留给 CPU/GPU 的原位入口检查。检查一次即可，不在 Verifier 里重新实现底层判断。错误信息指出哪条指令、哪个值和原因，不设计新的错误分类体系。

带新指令的 JSON 使用 V2；V1 继续可用，V1 中不能出现新指令或字段。沿用现有 JSON 解析规则。这次新增的内容只有：

```cpp
// ComputeOp 增加一个可选字段
std::optional<std::size_t> reuse_input;

// 增加一条释放指令
struct ReleaseOp {
    ValueId value;
};
```

不加入 wait 字段，不改 OperatorSpec 的版本和内容。所选 API 不支持某种原位操作时，在执行前明确报错。

## 6 编译器怎样标记原位和插入释放

在 placement 和通信插入完成后，增加一个 `plan-runtime-memory` Pass，放在导出 RuntimePlan 之前。

它做四件事：

1. 按导出器真正执行的顺序处理初始化、执行和返回，避免把初始化里定义的数据误判为已经用完。
2. 统计使用次数和最后一次使用的位置。
3. 给满足条件的计算加 `runtime.reuse_input=0`。
4. 在其他值最后一次使用后插入 `dist.release`，跳过最终输出和已经被原位覆盖的旧值。

同一个值如果初始化产生、执行阶段还要用，就在执行阶段最后一次用完后释放。初始化阶段已经用完的值，则在初始化阶段释放。

阶段的判断与导出器共用一个小函数。必要时先把初始化指令放到前面，保持同阶段原有顺序，并继续使用 MLIR 自带的验证。不做传输提前或延后，不增加新的返回位置选项；需要把结果取回 Host 时仍使用显式 D2H。

`dist.release` 没有结果。现有导出器默认每条操作都有一个结果，需要先单独处理 Release。导出器还要输出 reuse 字段和 V2 版本。

Release 应声明释放副作用，避免被当成无用操作删掉。这个 Pass 之后可以运行只读的峰值估算，然后导出，不再运行会合并、删除或重排计算的优化。重复运行内存 Pass 时直接报错。

## 7 在编译器里估算峰值内存

这项功能放在 dacapo 编译器中，新增一个 `estimate-runtime-memory` Pass。它直接读取已经分配好设备、插好传输和释放指令的 IR，以及编译时使用的 OperatorSpec，不需要先导出 JSON 再运行外部脚本，也不需要 GPU。

正常管线如下：

```text
数学优化和实际层级转换
→ 任务分配到各 rank 和设备
→ 插入传输
→ 标记原位并插入 Release
→ 估算峰值内存
→ 导出 RuntimePlan
```

估算 Pass 只生成报告，不改计算、不重新分配任务、不添加释放。不开启内存规划时，它也可以分析已经完成任务分配和通信插入的 IR，显示当前安排下的数据占用。

Host 内存按 rank 分开，显存按每张 GPU 分开；不把多卡各自的峰值加起来当作同一时刻的总峰值。如果后来改变了任务分配、传输或释放安排，就重新运行估算，不能沿用旧报告。

先算计划中明文和密文本身占用的空间。当前 Poseidon 的普通完整对象可以按这个公式计算：

```text
数据大小 = 多项式长度 × (level + 1) × 分量数 × 每个数的字节数

GPU 每个数 4 字节，Host 每个数 8 字节。
例如长度 65536、level 31、两个分量的密文：GPU 上占 16 MiB。
```

这些参数已经在 CKKS 类型、设备位置和 OperatorSpec 里，不需要再给 IR 加内存大小字段。公式使用已经转换好的实际 level，不能重复乘一次逻辑层级倍率。编译器已有计算通信数据大小的代码，可以复用其中的大小计算，并明确区分当前 Poseidon 后端的 Host 8 字节和 GPU 4 字节。

按下面的规则记账：

- 普通计算先加上输出的大小，再处理输入释放。计算过程中输入和输出会同时存在。
- Transfer 的源和目标分别计入所在设备；复制给几张卡，就分别计算几份。
- 原位计算继续占用原来的内存，新名字不重复加一份。
- 遇到 Release 就减掉对应数据。此处假设之前的操作已经完成；异步运行的区别见下文。
- 初始化阶段还没释放的数据继续计入执行阶段，最终输出继续保留。外部输入按调用方保留到本次运行结束计算，避免把解除借用误算成已经回收。

**第一版给出的是串行执行假设下的数据峰值，不是整个程序的实测显存。** 每条操作都假定完成后才执行下一条。多设备实际会并行运行，已经写了 Release 的数据也可能还在被读取，所以不能用这个数字保证程序一定放得进显存，它也不是任意并行调度下的严格下限。

报告同时给出“本次计划分配过的所有不同数据块之和”，作为所有这些数据都没来得及归还时的保守参考。原位链只算同一块一次。这个数也只覆盖计划内的对象，不是整个程序占用的上限。

密钥、参数表、Rotate 和 Boot 工作区、传输暂存区、编码数据缓存，以及内存池额外保留的空间都单独列为**尚未计入**，不会当作零成本并给出总显存承诺。后续需要更接近实机时，再补这些已知或实测的开销；尤其不能把原位 Rotate 的临时空间漏掉。

使用方式也接到编译器入口。建议增加 `--runtime-plan-memory-report` 选项：

- 开启后，`hecate-opt` 在导出 RuntimePlan 时，一并生成同名前缀的 `.memory.json`，并在终端打印简短结果。
- `generate_model_artifacts.py` 透传这个编译器选项，批量生成模型时也能拿到报告。
- 已经准备好的 CKKS/Dist IR 可以单独运行 `estimate-runtime-memory` Pass，方便检查不同设备分配方案。

以上选项和 Pass 尚待实现。估算代码放在编译器内的小模块中，让管线调用和单独运行 Pass 共用一份计算逻辑，不再维护另一套正式 Python 实现。

比较内存规划前后时，在同一次编译中记录两次：第一次在通信插入后、内存规划前；第二次在 Release 和原位标记插入后。两次都分析当时实际的 IR，不由估算器另行猜测该怎么释放或原位。如果要单独看原位的收益，就用关闭原位的内存规划配置再编译一次。

报告会给出每处峰值、峰值所在阶段和操作位置、当时明文与密文各占多少，以及最大的几个对象。最终报告中的 ValueId 和指令编号与 RuntimePlan 导出共用编号规则，避免用户看到的编号对不上。JSON 用字节保存，终端用 MiB 显示，并写明未计入的开销和串行执行假设。

## 8 按这个顺序实施

| 顺序 | 做什么 | 做到什么程度再继续 |
| --- | --- | --- |
| 1 | 给 RuntimePlan 加 Release 和 reuse，补解析及简单检查 | 旧计划能读，新计划能读，释放后使用和非法原位能报错 |
| 2 | 修改 API 的异步数据保留、完成后清理和通信交付 | 已完成工作不再一直占着数据；尚未完成的工作不会丢数据 |
| 3 | Runtime 执行 Release，处理多线程下尚未提交的使用 | 先用手写计划跑通，再验证多设备和多次发送 |
| 4 | 先接 Negate、AddCP/SubCP，再接 CPU/GPU Rotate 原位路径 | 连续三次使用同一组内存，结果与普通计算一致；Rotate 只保留必要的临时计算空间 |
| 5 | 编译器自动标记原位并插入 Release | 导出的计划可以直接交给 Runtime 执行 |
| 6 | 在编译器中加入峰值估算 Pass、选项和报告输出 | 按实际 IR 统计各设备占用，能比较内存规划前后，报告位置能对应到导出的计划 |
| 7 | 用已有模型和重复运行测试检查 | 数值正确，内存能回收，多跑几轮不持续积累；对照编译器估算说明实际开销 |

**当前已完成第 1、2 步，step 2 等待审阅。** 第 1 步的计划结构、
V1/V2 解析、打印和 Verifier 保持不变。协议、Schema 和 CPU/GPU 三次原位链
样例见 [`RuntimePlan V2`](../third_party/ckks-runtime/docs/runtime-plan/v2/specification.md)。

本次 step 2 的改动：

- **GPU API 按完成事件保留每次工作。** 输入、输出、Rotate/Rescale 的临时数据
  随对应事件保存；`collect_completed()` 只查询并清掉已完成工作，`drain()`
  等完所有已提交工作。计算和传输提交后、通信等待结束后进行清理。
  多步计算的临时对象在提交前登记；中途失败时先等当前执行流结束，再传播
  原错误，避免销毁仍在使用的对象。
- **通信结果只交付一次。** `posted_outputs()` 和 `wait()` 都返回与原
  `action.outputs` 等长的 optional 数组。已提前交付或属于其他 rank 的位置
  为空，其余本地结果由 `wait()` 交付；通信状态把值移出，不保留副本。
  Runtime 的串行和工作线程接收逻辑、CPU/GPU/Mock/MPI 后端及直接调用处
  已同步修改，重复交付、遗漏或错误位置直接报错。
- **完成后清掉暂存数据。** CUDA 传输请求完成后释放 pinned Host 暂存，依赖
  事件继续有效。D2H 构造 Host 结果后清掉下载暂存；NCCL 的发送源和 Host
  上传中转对象按每次发送事件保留，发送完成后可清理。CPU/MPI 发送结束后
  清掉序列化缓冲区，Mock 消息交付后从消息表移除。
- **整次运行收尾。** Runtime 等完所有通信后调用 `drain()`，包含不在最终
  输出依赖链中的计算。结果交给调用方后清空内部值表和通信状态，可以重复
  运行。Mock 的异步计算也会等完各工作队列，并传播未被最终输出观察到的错误。

**step 3 的 Release 执行、尚未提交使用的计数，以及 step 4 的原位入口尚未实现。**
含 Release/reuse 的计划仍会在提交 API 工作前明确报错；当前 Runtime 中间值
保留到运行收尾。step 2 解决的是 API 的异步引用和通信交付，不代表已经能
在计划最后一次使用后提前释放数据。

先用手写小计划验证 Runtime 和 API，再接编译器，出错时更容易定位。没有预取和强制等待释放，也就不需要原方案中的队列栅栏、双权重窗口和相关测试。

编译器估算功能可以先支持内存规划前的 IR，再接入带 Release/reuse 的 IR，最后与 Runtime 的内存记录比较。它不负责自动重新分配任务。

现有单卡 MLP 有 119 次 MulCP、2 次 AddCP、125 次 Rotate，没有 Negate。125 次 Rotate 的输入都有其他用途，按本次规则没有能直接原位执行的候选。因此这个模型先看释放中间值的收益。

已有单卡 `probe-1gpu-1999` 计划中的 1600 次 Rotate 按使用次数和描述符检查都符合候选条件，可以用来验证连续旋转复用内存的效果。这只是计划统计，实际布局和运行结果还要测试；不能把它当作 MLP 的收益。

## 9 保留这些测试就够了

- **释放安全：** 故意让一个 GPU 计算或传输晚一点完成，确认 Release 不会让它读到已回收的数据；完成后确实会清理。
- **线程间交接：** 另一线程还没提交计算，或者一个复制操作还有后续发送没提交时，源数据仍然存在。
- **真实原位：** 支持的操作都与普通计算结果一致；连续三次覆盖使用同一组内存，没有完整结果临时副本。Rotate 允许必要的排列和密钥切换工作区，并单独记录它们占用的空间。
- **错误能报出来：** 释放后使用、覆盖后使用、释放最终结果、原位输入还有别的用途，以及不支持的原位操作。
- **通信能清干净：** 提前交付的 GPU 结果不重复交付；Host 下载临时区和发送端数据用完能释放。
- **编译器插入正确：** 跨初始化和执行阶段的值不会提前释放；被覆盖的旧值不再插 Release；最终输出保留。
- **整次运行收尾正确：** 包括不影响最终输出的工作也已经完成；调用方丢弃每轮结果后，多跑几轮不会一直增加活跃对象。

保留旧计划的回归测试。对新旧计划比较最终计算结果即可；要求保留所有历史值的调试模式与原位冲突，遇到这类组合直接报错。

释放测试看内存是否已归还给分配器，以及 API 是否还持有数据。缓存池可能把归还的显存留着复用，所以不能只看 `nvidia-smi` 的数字有没有下降。未实际运行 GPU/MPI 的项目，要明确记为未测。

编译器估算功能用几个能手算的小 MLIR 用例验证：输入输出同时存在、原位不重复计数、跨阶段保留、每张卡的复制分别计数，以及外部输入仍由调用方持有。把报告检查接到编译器的 `test/runtime-plan/check.py`，再验证两种不同设备分配会得到对应的分设备结果。现有 Python 原型及其测试可作为迁移参考，但 Python 测试通过不代表编译器功能已经完成。
