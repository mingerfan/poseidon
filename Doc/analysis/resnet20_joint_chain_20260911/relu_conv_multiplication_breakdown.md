# ReLU / Conv 每个乘法节点的 scale 分解

## 先明确入口和验证范围

这份 Q50 见证的 ReLU **输入 log2(scale)=40，不是 53.030946**。
53.030946 是 EvalMod 按内部算术得到的出口 scale；见证在生成 EvalMod 常数时
已加入输出幅度补偿，然后才把出口 scale 变为 40。
这不是允许将一个未经补偿、已经生成的 scale=2^53.030946 密文免费改成 2^40。

补偿参数：α=2^(40-53.03094629532368)=0.00011947974670083945，
r=α^(1/4)=0.10454988833538781。多项式所有系数乘 r，
两次 DA 常数分别乘 r^2 和 r^4，则理想算术输出为原函数的 α 倍；
出口 scale 同时乘 α，才保持表示的函数值不变。

下表属于**拟采用的 22-Q ReLU 静态调度**，不是当前应用 GPU 跑出来的轨迹。
特别是，明文系数不是全部使用 2^40 编码，而是按分支对齐和目标出口反推各自的编码 scale。
应用代码尚未接入这份逐节点调度；没有验证真实密文误差。

## 表格约定

- 所有数字均为 s=log2(scale)。乘法是 s_a+s_b，rescale 是减去所删除实际素数的 log2 之和。
- `a+b; c+d` 表示两次不同的乘法；两项乘积的 scale 相同，随后相加，共享该行 rescale。
- 明文叶节点中的第一个数是密文基的 s，第二个数是明文系数编码的 s，不是系数值。
- `Tj` 是本阶段输入的 Chebyshev 基。不同阶段的 Tj 不是同一密文。
- 基构造中的乘 2 可以由加自身实现，不改变 scale；常数 1 按加法位置的 scale 编码。
- 合并节点写出的加法支路，已经在此前节点形成，并与乘积 scale 对齐；加法不再消耗 Q。
- 不同表行可能是并行分支，Q 不按整张表单调递减；没有升模。
  各行删除 Q 数不能相加当作链深度，链深度应看依赖路径。
- 为可读性保留六位小数；内部检查使用未截断数值。

## ReLU 最后一次乘原始输入 x

这里 x 是整个 ReLU 的原始输入，s=40，而不是第三段的输入 s=44。
将保留的 x 降 Q 对齐到 Q12，不做 rescale，因而其 scale 仍是 40。

| 操作 | scale 变化（log2） | Q 变化 |
|---|---|---|
| P27 * x | 89.87112238710051 + 40 = 129.87112238710051 | 12→12 |
| 除 q[11]=1043464193 | 129.87112238710051 − 29.958733948525538 = 99.91238843857498 | 12→11 |
| 除 q[10]=1042415617 | 99.91238843857498 − 29.95728345697241 = 69.95510498160257 | 11→10 |
| 除 q[9]=1040842753 | 69.95510498160257 − 29.955104981602638 ≈ **40** | 10→9 |

P27 出口 89.871122… 是与这次乘法联合设计的，不是运行碰巧得到的值。
若删除素数的乘积为 R，规划器要求 `S_P27 * S_x / R = 2^40`，
再反推叶节点明文编码 scale，并检查各分支能否在这组 Q 上实现。

## ConvBN：保持入口 scale，而不是把任意入口降到 40

权重、支撑掩码、选择掩码按将被删除的实际模数编码：

| 明文 | 编码 scale | log2(scale) |
|---|---:|---:|
| 权重 | q[8]=4267442177 | 31.99072445913839 |
| 支撑掩码 | q[7]=4266393601 | 31.990369923278514 |
| 选择掩码 | q[6]=4265476097 | 31.990059632914793 |

| 操作 | 输入 s / 明文 s | 输出 s | Q 变化 |
|---|---|---:|---|
| 每个权重乘法，随后累加 | 40+31.990724459 | 71.990724459 | 9→9 |
| 每个支撑掩码乘法，随后累加 | 71.990724459+31.990369923 | 103.981094382 | 9→9 |
| 第一次 rescale | 103.981094382−31.990724459 | 71.990369923 | 9→8 |
| 第二次 rescale | 71.990369923−31.990369923 | 40 | 8→7 |
| 每个选择掩码乘法，随后累加 | 40+31.990059633 | 71.990059633 | 7→7 |
| 第三次 rescale | 71.990059633−31.990059633 | **40** | 7→6 |

卷积通道/核位置的同类乘法共用表中 scale。旋转、relinearize、同 scale 加法、
按相同 scale 编码后的 bias 加法不会改变上述 scale 账本；不代表它们没有数值误差。

一般地，输入 S 时有 `S*q[8]*q[7]/q[8]/q[7]*q[6]/q[6]=S`。
**所以输入 2^53.030946，输出仍是 2^53.030946；没有自然回落到 2^40。**

## 独立前向重算与不能声称的结论

本次重新读取见证，使用 70 位 Decimal 精度计算实际素数的 log2，
从第一个输入开始逐乘法向前传播，叶节点只采用已选定的编码 scale，
没有在每个阶段结束时用目标值覆盖计算结果。检查并行分支的加法 scale 对齐。

前向结果（保留已保存的有限位编码参数）：

```
第一个 P15：40.099999999999953...
第二个 P15：43.999999999999284...
P27：      89.871122387082605...
ReLU：     39.999999999982021...
Conv：     39.999999999982018...
```

相对保存的双精度规划值，最大 log2 差约 1.80e-11，最终 scale 相对 2^40 的偏差约
−1.25e-11。这是有限位规划参数的数值一致性检查，不是 GPU 元数据实测，更不是
密态结果误差测试。严格说应称“浮点容差内为 2^40”，而非保证位级完全等于 2^40。

若不做前述 EvalMod 系数补偿，而将 53.030946 直接送入本表固定参数：
第一段 T2 就会变为 `2*53.030946−29.999648=76.062245`，不再是 50.000352；
后续 Chebyshev 修正/多项式支路也不再满足本表的 scale 对齐。
不能沿用本表的 22-Q 结论。
