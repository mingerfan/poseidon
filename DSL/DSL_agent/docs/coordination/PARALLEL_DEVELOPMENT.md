## 责任边界

| 工作 | 通用化线 A | 整模型线 B |
|---|---|---|
| JSON、受限源码、可信 PyTorch 接入与等价写法 | 实现与维护 | 提供真实整模型输入和缺口案例 |
| 注册、递归分解、循环/膨胀/来源可靠性 | 实现通用规则 | 对真实网络作黑盒组合验收 |
| 通用算子和 DSL 构造 | 每个新增分区至少三个上下文 | 使用已发布能力，不编写模型专用 lowering |
| 大权重、布局、容量、跨密文运算 | 实现通用机制和预测 | 定义目标规模、收集真实资源数据 |
| 近似/应用精度接口及终态策略 | 实现分项度量、要求、拒绝与预算控制 | 校准具体网络、冻结近似与数据、评估准确率 |
| Bootstrap/CUDA 的 Agent 适配 | 根据已认证后端能力接线与交付 | 审计库与 Runtime 公共接口，执行后端认证与整网测试 |
| MLP、RMSNorm、Attention、ResNet20 | 提供公共组件能力 | 拥有模型、数据、验收和程序包 |
| 多模型族、未见组合 Benchmark | 维护能力评测与通用性统计 | 贡献整模型报告，引用公共证据 |
| 全局预算/身份/缓存/任务/取消 | 单一可信控制层 | 通过控制层调用，不另建 Agent |
| 后端库、参数、依赖升级 | 两线均先提出具体方案，经单独批准再实施 | 同左 |

所有通用算子代码只在 A 实现。B 发现缺口时给出版本化最小复现和能力请求；A 交付能力版本后 B 继续原案例。两线共享检查器和后端服务，报告按绑定引用；不重复生成同一模型或把旧结果改成新版本通过。

## 并行运行

两个分支需要两个独立工作目录；不能在同一 checkout 同时切分支或改代码。设计阶段已完成，本次仅建立获准的本地集成提交，不创建共享 DSL、功能分支或 worktree。
建议以后在 Ubuntu 使用独立 Git worktree，路径可为 /home/lhohy/Code/Poseidon-generalization 和 /home/lhohy/Code/Poseidon-resnet20；实际创建另行确认。

各工作目录绑定独立源码、任务、缓存、构建和结果身份。相同平台、源码和依赖身份的只读 SDK 可复用；CMakeCache、venv 和可写构建不可跨架构或跨身份混用。
旧结果、旧 SDK 和原始 Provider 响应保持原样；新源码产生新绑定。

全局上限为证据 48 GiB、磁盘余量 4 GiB、每例/每批 4 GiB、编译 2 jobs、链接 1 job、API 和密态执行默认串行。两个分支的上限不相加。
并行开发先于并行后端执行。启用任何执行前，A 必须提供共享锁和总账本；两线在共同 work root 下登记预留、实际消耗和终态，绑定计划哈希。源码冻结期间只能运行其冻结快照。
Nix launcher 的现有锁保持；不为并行关闭沙箱或锁。

已有“计划内全部离线和真实测试”授权继续在原计划范围生效。每批仍先冻结案例、代码、依赖、请求和调用预算，最多 3 轮修复、每次最多 3 次传输重试；常用单次 1200 秒/384000 tokens。无货币硬上限，传输重试可能重复计费；旧未知调用不重试。
新安装、下载、数据/权重、后端修改、安全参数、资源扩大、提交、推送和 PR 保留独立批准边界。网络、代理、DNS、路由和 VM 网络配置保持不变。
