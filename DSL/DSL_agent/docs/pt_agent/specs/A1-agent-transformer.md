# A1：Transformer 上的近似优化与 Agent 的 LLM 运行（阶段 1）

Claude 于 2026-10-27。用户的决定：

- 分两个阶段。阶段 1 是近似优化加上 Agent 调用 LLM（即本 spec）；阶段 2 是 token 打包布局，另写 spec。
- 本轮 LLM 预算为**每个模型 40 次，共 80 次**。当前累计 129/450。

## 0. 目标与原则

- 对 U4 的两个模型（BERT-tiny、tiny Qwen2）：
  1. 加入**通用的**近似优化；
  2. 让 Agent 按冻结协议真正调用 LLM 生成 PT-DSL，经过精调和确认后冻结；
  3. 与规则基线对比自举数、深度、预测延迟和精度。
- 通用性原则不变：所有规则都写成与模型无关的公式，不针对某一层、某个样本或某个模型。
- 数据划分沿用 model_info 中的 calibration、heldout、confirm、report：
  - 定义域只来自 calibration；
  - 精调只看 heldout；
  - 冻结时只用一次 confirm；
  - report 只在冻结之后评测一次。
- 判据沿用 model_info 的 threshold（例如 Qwen：`agreement_pct ≥ 99`、`logit_rel_err ≤ 0.01`），并保留 max_u ≤ 0.90 和不发散的要求。**容差和判据都不放宽。**
- 注意：Qwen 的 U4 规则程序 logit_rel_err 已经是 0.0083，余量很小。降低近似精度时，以判据为准。

## 1. 通用优化：softmax 归一化的误差预算

### 1.1 依据（严格成立）

在 §11.6 的反复平方形式中，每次归一化 `p ← q · inv(Σq)` 对每一行乘的是**同一个标量**。设近似的 inv 有相对误差，使该行乘上 `c = T·inv(T) ∈ [1−ρ, 1+ρ]`，则：

- 下一步的 `q' = c²·q_true`，`Σq' = c²·Σq_true`，归一化之后 c 被**精确抵消**；
- 只有链条中**最后一次**归一化的误差会留在输出里；
- 第一步 inv（S0）和第 1 到第 k−1 步只需要把数值控制在有界范围内，不需要 1e-3 的精度；
- k=0 时，第一步 inv 就是最后一次归一化，仍需要 1e-3。

逐元素的误差（exp 的近似误差和 CKKS 噪声）仍按 2^k 放大，因此 exp 的目标 `1e-3/2^k` 不变。

### 1.2 DSL

softmax 新增可选的 `final_inv_method`、`final_inv_domain`、`final_inv_*`（包括 `final_inv_fit`）。语义如下：

- `steps = k > 0` 并且给出了 final_inv 时：第 1 到第 k−1 步用 step_inv，第 k 步用 final_inv；
- 没有给出 final_inv 时：k 步都用 step_inv，与 U4 完全相同；
- 默认不出现这些字段，所以既有程序（包括 U4 的 BERT 和 Qwen 规则程序）的 Emit 逐字不变；
- Mock、张量引擎、Emit 和 P2 结构相同；诊断按 `::final_inv` 记录；
- parser 增加对应用例，r8-v7 提示词说明这些字段和 §1.1 的依据（用通用表述，不提具体模型）。

### 1.3 定义域与目标（通用公式；n 为 key 数的上界 Lk，ρ 为中间预算）

- 第一步 inv：定义域仍为 §11.6 和 §11.7 的解析界。k > 0 时目标为 ρ；k = 0 时目标为 1e-3。
- step_inv 和 final_inv 的定义域都取 `[(1−ρ)² / (1.5·n), 1.5·(1+ρ)²]`。这是因为前一步留下的标量 c 会使 `T ∈ c²·[1/n, 1]`，再加上正值输入的 margin。
  - step_inv 的目标为 ρ；
  - final_inv 的目标为 1e-3。
- ρ 的阶梯为 {0.5, 0.25, 0.1}。ρ 写进 DSL 的 `inv_budget=<float>` 属性（只在 k > 0 且给出 final_inv 时有效，供诊断和精调读取），不改变运算语义。
- 所有点的方法、fit 和阶梯都与 §11.2、§11.8 相同，上限也相同：iters ≤ 5、阶数 ≤ 63、k ≤ 8。

### 1.4 k 的选择

k 取 0 到 8 之间的任意值（不再要求 k ≥ k0）。在满足以下条件的 k 中，选**预测延迟最小**的一个：

- exp 的定义域为 `[a0/2^k, b0/2^k]`，exp、第一步 inv、step_inv、final_inv 都有可行候选；
- 延迟用现有的成本模型（§7.8 的规范化）静态计算，不需要数值运行。

### 1.5 两个规则基线（都用于论文对照）

- **R0**：U4 现有的规则程序，原样保留，不重新生成。
- **R1**：R0 加上本节的规则：ρ 固定为 0.25，k 按 §1.4 选择，act、rsqrt 和其余规则不变。

R1 由规则规划器的一个新选项生成，默认关闭，所以 R0 的生成结果不变。R1 在 heldout 上的结果**原样汇报**，不通过也照实记录。

### 1.6 测试

- 恒等式测试：exact 模式下，把中间各步的 inv 换成乘上随机 `c ∈ [1−ρ, 1+ρ]` 的精确倒数，输出与 `steps=0` 的差在数学容差 1e-12+1e-12|ref| 之内；覆盖 mask 和 causal 两种情况，k=1..8；
- 定义域公式和 k 选择的单元测试；
- 用解析界算出的定义域要覆盖校准中的实际输入；
- `final_inv` 缺省时，Emit 逐字不变。

### 1.7 补充：数值退化的候选（Claude 于 2026-10-27，对应 `A1-qwen-prepare-20261027T123519-ad8a`）

**现象**：Qwen 第一个 softmax 在 k=0 时，未缩放的 exp 定义域约为 [−521, 86]，第一步 inv 的比值约为 32·e^606。在这样的定义域上拟合，系数会出现数值退化。`_relative_profile → cheb_eval` 因此抛出"Chebyshev coefficients reduce to a constant"，规划随之中止。

**规则**（与 §11.4 对未收敛候选的处理一致，通用，不针对 Qwen 或 k=0）：

1. 单个候选在拟合、系数生成或误差评估中出现以下任一情况，就判为**不可行候选**：
   - 抛出 `KernelError`、`ApproximationError` 或 `FloatingPointError`；
   - 系数中含有非有限值；
   - 误差评估得到非有限值。

   不使用这个候选的系数，不重试，也不改变拟合方法或判据。
2. 记录内容包括：role、fn、fit、method、degree（或 deg0/iters）、domain、target，以及所在的 k 和 ρ。reason 写 `"degenerate"`（非有限值写 `"nonfinite"`），同时记录异常类型和消息。
3. 这个候选失败后，继续同一点的其余既定阶梯（其他阶数和 fit）。同一点所有候选都不可行时，该点为 infeasible，所在的 (k, ρ) 组合也随之不可行。§1.4 继续评估其他 k，**全部 k 都算完**之后再选择。只有当某个 softmax 在 0 到 8 的所有 k 上都不可行时，才按 §11.3 停下汇报。
4. 只捕获第 1 条列出的异常和非有限值检查。其他异常类型（如 `TypeError`、`KeyError`、`IndexError`）说明实现有错，仍然要停下。
5. 精调器的移动、Agent 提出的程序中，遇到同类数值退化时，记为该候选或该程序**不可行**：
   - 精调器拒绝这一步移动；
   - Agent 收到结构化反馈，包括出问题的行号、role、domain 和原因；
   - 进程不崩溃，这一轮也照常计入调用预算。
6. 已有的可行候选，以及 R0、U4 的程序和既有测试，都不受这条规则影响。增加一个单元测试：构造会触发退化的极宽 exp 定义域和 inv 定义域，确认得到 `infeasible`，记录完整，并且搜索继续到其他 k。

**接续**：本轮已通过的 21 项离线测试保留。补上第 6 条的测试后，从 Qwen 的 prepare 开始重跑，再按 §3 继续。真实 API 调用仍然从 0 开始计数，预算不变。

### 1.8 补充：inv 理论诊断的数值稳定公式（Claude 于 2026-10-27，对应 `A1-bert-unit-20261027T125718-eb96`）

**现象**：比值 r≈9.40e264 时，`q=(r−1)/(r+1)` 和 `(r+1)/(r−1)` 在 float64 中都舍入为 1，`log(q)=0`，`acosh(...)=0`，于是在 `transformer_rule.py:131` 抛出 ZeroDivisionError。

**结论**：这是**诊断公式本身的数值实现问题**，不属于 §1.7 第 1 条所说的候选退化。**不扩大 §1.7 的捕获范围**，改用以下数学上等价、数值稳定的公式：

- `log q = log1p(−2/(r+1))`
- `optimal_constant_newton_iters = 0`（若 q ≤ target），否则为 `ceil(log2(−ln target) − log2(−log q))`。这里在对数域相减，避免 `ln target / log q` 溢出。
- `acosh((r+1)/(r−1)) = log1p(e + sqrt(e·(2+e)))`，其中 `e = 2/(r−1)`
- `relative_minimax_polynomial_degree = ceil(acosh(1/target) / 上式) − 1`

对 r = 342.2334589845186、target = 1e-3，Claude 用标准库核对过，稳定公式给出 11 次迭代和 70 阶，与原公式和已有记录相同。对 r = 9.4e264，结果约为 883 次和 1.17e133 阶；r 直到 1.7e308 都是有限值。

**记录规则**：

1. 结果 ≤ 2^53 时，记为整数。超过 2^53 时，记为浮点值，并加 `"approximate": true`，因为整数已不精确。
2. 只有当 r 本身非有限、r ≤ 1 或定义域下界 ≤ 0（例如 e^a 下溢为 0）时，该项才记为 `null`。同时保留 domain、比值（可表示时）、公式文本，以及 `reason`（`"ratio not finite"`、`"ratio <= 1"` 或 `"nonpositive lower bound"`）。
3. `polynomial_formula` 和 `newton_formula` 字段改写为上面的稳定形式，并注明"与原式数学等价"。
4. 理论诊断只做记录，不参与选择。可行性判定和既有选择结果都不变。

**测试**：

- r 取 342.2334589845186 和 144.2694173659632 时，结果与原公式（以及已有的 U4 记录）相同；
- r 取 9.4e264 和 1.7e308 时，结果为有限值，并带 approximate 标记；
- 定义域下界为 0 和 r 非有限时，记为 null，并带 reason；
- 都不再抛出异常。

**接续**：补上测试后，从 BERT 的单元测试组重跑，再按 §1.7 的接续继续 Qwen prepare 和 §3。真实 API 计数和预算不变。

## 2. 精调器（`planners/transformer_tuner.py`）

在现有的逐点降阶之外，增加 softmax 级的移动：

- k 加减 1；
- ρ 在阶梯上移动；
- 第一步 inv、step_inv、final_inv、exp 在 §11.2、§11.8 的阶梯内换方法、阶数或 fit；
- act（cheb）和 rsqrt 的降阶沿用现有规则。

每个候选的定义域都按 §1.3、§1.4 和校准数据重新计算，**不用 heldout 修改定义域**。

接受条件：

- 预测延迟下降；
- coarse 和 full 两级 heldout 验证都满足 threshold，max_u ≤ 0.90，且不发散；
- 覆盖失败（§11.5）就不接受。

搜索顺序和预算沿用现有的 tuner（budget_s、max_sweeps），history 记录每一步的移动。

## 3. Agent 的 LLM 运行

### 3.1 准备（不调用 LLM）

- `run_agent` 允许 r8-v7 使用 `engine_profile="tensor"`。现在的限制是只允许 r8-v5 和 r8-v6；r8-v4 到 r8-v6 的行为保持不变。
- token 模型从 U1 入口进入 Agent 流程：Agent 规划 → tune → confirm → report 评测 → export → compiler 模式编译 → managed 模式编译。目前 `transformer_run.inside` 只支持规则流程，需要接入。
- 用录制的假客户端做离线回放测试：覆盖成功、不可行反馈、预算耗尽、解析失败这几条路径，不发起真实调用。
- 提示词中不得出现目标模型自己的规则程序（R0、R1）。示例库沿用"排除目标模型"的规则。
- 完成后**冻结 r8-v7**，此后不再修改提示词、能力表、反馈格式、tuner 和 confirm。在 STATUS 中记录冻结时的文件清单。commit 和 tag 由 Claude 在用户批准后处理。

### 3.2 运行协议（每个模型独立执行）

- **配置**：DeepSeek，thinking 开启，参数沿用冻结协议。凭据只经批准的 loader 从项目根目录的 `.env` 读取，不打印、不传输、不提交。
- **预算**：每个模型 40 次调用，在客户端包装层硬性计数。用完就停，不追加。registry 中记录每次调用。
- **会话**：每个会话的 max_iters 为 8。只有当前一个会话没有得到通过 confirm 的程序时，才开新会话。得到通过 confirm 的冻结程序后，该模型即停止，剩余额度在汇报中给出。
- **精调**：沿用现有的 tune_policy 和 tuner 流程；engine_profile 为 tensor，最终用 Mock 复核。
- **确认**：候选按预测延迟从小到大依次在 confirm 上评测，第一个满足 threshold 的冻结。
- **报告**：冻结之后，在 report 的 160 条样本上用 Mock/tensor 评测一次，然后进行 compiler 和 managed 两种模式的编译。
  - 预测、compiler、managed 三方的自举数和切点必须一致，并比较完整的 RuntimePlan；
  - 运行 managed 之前先报告 IR 大小，按 §7.5、§7.6 和 §7.9.5 的规则执行。
- R0 和 R1 也在同一组 report 样本上各评测一次，并各自编译。

### 3.3 停止规则

以下情况停下汇报，不自行扩大范围：

- 某个模型用完 40 次调用仍没有通过 confirm 的程序；
- 冻结程序的编译失败，或三方自举数不一致；
- 内存或磁盘准入失败（按 §7.10 的口径）；
- 发现需要修改编译器、运行库或判据才能继续。

### 6.1 输入接口（对应 a）

- r8-v8 的图摘要新增 `inputs`：按原模型 forward 顺序列出**全部**输入，每项给出 name、shape、kind（tokens/mask/image/vector）、DSL 类型（`Cipher` 或 `Mask`）和允许的 pack 布局。信息取自已有的 model_info inputs，不新增输入来源。r8-v4 到 r8-v6 的摘要不变。
- 提示词中由注册表生成一条规则：函数签名必须使用这些名字、这个顺序和这些类型，不得改名、增删。
- 新增接口检查（反馈阶段 `interface`），位于 parse 之后、typecheck 和任何执行之前：参数的名字、顺序、类型、形状与模型输入逐项比较，不一致时返回 feasible=false，并给出期望与实际的对照；**不抛异常**。tuner、confirm、report、export 入口也调用同一个检查，不一致时停止（正常流程下不会出现）。
- 测试：第 37 次的程序得到 `interface` 反馈，不再出现 KeyError；把 Mask 声明为 Cipher 时，反馈里给出 Mask；R0、R1 两个模型都通过接口检查。

### 6.2 能力表与检查器一致（对应 b、c）

- 每个 fn 可用的方法由内核的实际支持表生成（cheb 用 `poly.EXACT` 的键，remez 和 newton 用各自的表），写进能力表文字，不手写。
- typecheck 新增 `E_METHOD_UNSUPPORTED`：方法不支持该 fn 时，在数值预检之前拒绝，消息里列出该 fn 可用的方法。§1.7 的 "degenerate" 只用于受支持的 fn 上真正的数值退化。
- `add(a,b)` 的说明改为：b 可以是同布局的密文，也可以是逻辑形状与 a 相同的公开 `W[...]`；`bias` 只用于最后一维的向量。Mask 的说明写明：只能 `pack(..., layout="flat")`，只能作为 softmax 的 `mask=`。
- 通用要求：每个由约束触发的 typecheck 检查都附一段说明文字，并自动写进对应算子的能力表条目。测试遍历所有检查，断言它们的说明文字都出现在生成的提示词里。不为某个模型单独写说明；测试同时断言提示词中除图摘要之外不出现目标模型的权重名。
- 不给 cheb 增加 inv/rsqrt 支持，因为这会改变 R0、R1 的选择阶梯。

### 6.10 速度优化：先于 §6.9 接续执行（Claude 于 2026-10-28，用户要求"先优化速度"）

**剖析证据**（Claude 在 codex 空闲时于本机 Nix 中一次性测得；BERT，第 13 次程序，单进程，峰值 678 MiB）：

| 部分 | 耗时 |
|---|---:|
| 静态成本估计 `estimate`（不用缓存） | **32.7 秒** |
| 　其中 lowering 构建 DAG | 30.1 秒 |
| 　其中 `Backend.const`：180342 次调用，每次对 16384×8 字节做 `_vector` 复制、校验，并算 blake2b | **19.6 秒** |
| 　其中 depth_dp 放置 | 1.0 秒 |
| tensor 留出集验证（20 条） | 0.13 秒 |
| 精确检查 | 0.04 秒 |

所以 tuner 每个候选的时间几乎全花在成本估计上，主要是给常量去重时的哈希（每次估计约 23 GB）。另外，所有 A1 精调都用满了 2400 秒（实际 2577–2649 秒），也就是说**一轮扫描都没有走完**，是被时间截断的。

**1. 常量去重的快速路径（必须做）**

- kernel 产生的公开向量（线性层对角线、掩码、广播常量等）在 kernel 层按输入记忆化（权重名、对角线序号、布局参数），返回**只读**的 ndarray。TokenLayout 下，同一组对角线对每个 token 重复使用，重复率预计约 40 倍。
- `Backend.const` 增加身份快速路径：传入的是本后端已经见过的只读 ndarray（按对象身份判断，并持有强引用，避免 id 被复用）时，直接返回已有的 Plain，不复制、不校验、不哈希。其他输入走原路径（校验 + blake2b），保持不变。
- `CostDag.const` 去掉重复的 `_vector` 调用。
- 去重语义必须与现在完全一致：内容相同的常量得到同一个名字，命名顺序也相同。

**2. lowering 前缀复用（可选，按实测决定）**

- tuner 的候选只改一个 op 的近似参数。可以保存当前已接受程序在各 op 之后的 lowering 状态，候选从改动 op 的前一个快照开始继续。
- 只有满足以下两条才启用：成本估计时间再降 ≥30%，并且快照内存加上峰值不超过 4 GiB（Qwen 当前峰值 3.35 GiB，要单独测）。否则不做，在汇报中给出实测数据。
- 不做多进程并行：本机 7 GiB 内存放不下两个 Qwen 进程。

**3. 等价性要求（不满足就不能合入）**

- 对以下程序，`estimate()` 的完整结果逐项相同（自举、切点、深度、旋转、各类运算计数、distinct_consts、预测延迟、成本分解），DAG 编号也相同：
  - BERT 和 Qwen 的 R0、R1；
  - r8-v7 的 26 份程序和 r8-v8 已有的全部程序；
  - 冻结的 CNN 程序和集合 M 中能在本机运行的部分。
- tuner 决策等价：只在测试中加一个"按评估次数计"的预算。同样的次数预算下，新旧实现的 history、changes 和结果必须完全相同。正式运行仍用 2400 秒的时间预算。
- 原有 64 项测试和 §6.9 的新测试全部通过。

**4. 口径**

### 6.11 精调触发与起点不可行时的处理（Claude 于 2026-10-28，用户决定"两项都做"）

**依据**

- 到目前为止，A1 一共精调了 6 次（含 r8-v7 的 1 次）。起点不可行的 4 次全部 0 接受，每次约 2600 秒；起点可行的 2 次分别接受 5 处和 6 处修改。r8-v8 下，BERT 约 43% 的墙钟时间花在了起点不可行的精调上。
- 原因有两个：
  1. CNN 的 `tuner.py`（R8e 起）在起点不可行时只做一次定义域对准，失败就立即返回。`transformer_tuner.py` 在 A1 路径上用 `elif not initial['feasible'] and not a1` 跳过了这次返回，于是一直扫到预算用完。spec 没有规定起点不可行时的行为，是 spec 留下的空白。
  2. `new_llm_best` 和 `llm_min` 把不可行、甚至发散程序的成本也算进去了。结果是：第 1 次（不可行）被精调，第 7 次（可行）没有被精调；第 10 次（发散）的成本压住了第 11、12 次。

**修改 1：起点不可行时，修复一次，失败即返回（与 CNN 一致）**

- 只改 r8-v8 的 A1 路径，去掉 `not a1` 例外。
- 起点不可行、但没有发散且精确检查通过时：做一次现有的定义域对准，仍按校准数据，不用 heldout，见 §2。
  - 对准后可行：采纳对准结果，**不要求成本不升**（起点不可行，没有可比的成本基线），然后继续正常精调；
  - 对准后仍不可行：立即返回原程序，feasible=false，history 只含 domain 一步。
- 起点可行时，行为完全不变：对准需要可行且成本不升，才会被接受。

**修改 2：`new_llm_best` 只在可行程序之间比较**

- `llm_min` 只由 feasible=true 的 LLM 原文更新。不可行或发散的程序，`new_llm_best` 恒为 false。
- 触发公式不变：`eligible and (new_llm_best or not has_tuned)`。所以每个会话里第一个 eligible 的程序（可行或不可行）仍会触发一次精调；不可行的那次按修改 1，很快就会结束。之后每出现一个新的、最快的**可行**程序，都会被精调。
- tune_cache、eligible 的定义、tuner 的移动顺序与接受条件、confirm 都不变。

**范围与口径**

- 只影响 r8-v8。r8-v4 到 r8-v7 和 CNN 的 `tuner.py` 不变，用回归测试证明。
- 提示词和反馈文本不变，版本名仍为 r8-v8。冻结清单附录写明"§6.11 决策修订"，并列出改动文件。

- 会话状态迁移：从 SESSION.json 恢复时，按新定义用 history 重新计算 `llm_min`（只取可行的原文），新旧两个值都记录下来。第二会话中，第 12、13 次是可行原文，新的 `llm_min` 是 3233700613；它与旧值碰巧相同，在汇报中写明。

**测试（离线，不调用 API）**

1. 起点不可行、对准后仍不可行：在 1 次成本估计和 1 次验证之内返回，history 只含 domain。
2. 起点不可行、对准后可行：即使成本升高也采纳，然后继续正常精调。
3. 起点可行：用按评估次数计的预算，与修订前的 history、changes 和结果完全相同。

### 6.12 解析点越界的上游预算判定（Claude 于 2026-10-28，对应 `A1-transformers-s611-stop-20261028T123153-bb2b`）

**本次停止的原因（Claude 离线核算，未调用 API）。** 第 21 次程序第 12 行 softmax 设置 `inv_budget=0.5`，即声明初始 inv 的相对误差不超过 0.5；step_inv/final_inv 的解析域 `((1-ρ)²/(1.5n), 1.5(1+ρ)²)` 就是在这个前提下推出的。但它选的初始 inv（newton，deg0=7，iters=4，相对拟合，域 [1.4989e-5, 1]，两端相差约 6.7e4 倍）达不到这个预算：
- 初值的相对误差在整个域内等幅振荡，最大约 0.998，迭代 4 次后约 0.970；
- 在观测输入范围 [4.1e-4, 0.135] 内，行和 c = x·inv(x) 最低约 0.030（x≈0.038）；
- 由 Cauchy–Schwarz，step_inv 的输入 Σp² ≥ c²/n ≈ 2.28e-5，与观测最小值 3.4e-5 一致。

所以解析式本身没错，是上游近似没有满足该推导所依赖的预算，属于候选程序的缺陷，不是基础设施错误。验证一致率仍是 20/20，因为逐行的常数会在下一次归一化中抵消，误差只体现为后续定义域越界。codex 实施前须按 ① 复核，复核结果不一致时停止汇报。

另发现一处来源判定的浮点问题：该行 inv 声明的域上界为 1.0（能力表公式给出的值），代码算出的解析上界为 1.0000000000003284，"声明域包含解析域"的判定因 3e-13 的舍入差而失败，该点被判为 calibrated 并按 0.90 的门限计（实测 0.9992）。

**① 诊断（离线，API 零新增）。** 对 `A1-bert-session-20261028T110734-9ce8/sources/iteration-5.ptdsl`，在同样 20 个留出样本上用 tensor 引擎重算，记录：

**② 判定规则（仅 r8-v8）。**
- **解析域的前提**：step_inv[i] 和 final_inv 的解析域假设上一级逆输出的行和 c 落在 R 内。i=0 时上一级是初始 inv，c = (S/inv_scale)·inv(S/inv_scale)；i≥1 时上一级是第 i−1 步的逆，c = total·inv(total)。有 `inv_budget=ρ` 时 R=[1−ρ, 1+ρ]；没有 inv_budget 时（只允许在没有 final_inv 的情况下）R=[√(2/3), √(3/2)]，即 1.5 余量对应的范围。
- **分类**：某样本的首个越界点（§6.9 口径）是 step_inv/final_inv，且同一 softmax 中上一级的 c 在该样本上超出 R 时，首个越界改记为上一级逆，类型为 `kind="budget"`（行号和 role 写上一级的），越界链接着列出下游的解析点。这一情况按 §6.9 的普通越界处理：拒绝候选，不停止。上一级的 c 都在 R 内而下游仍越界时，仍按 §6.7 停止。

### 6.14 精调提速：剔除被支配的 softmax 候选、单次精调收敛、复用已收敛结果（Claude 于 2026-10-28，用户要求"减少精调、加快速度"）

**依据（BERT 第三个会话，split-v1，第 17–21 次）。**
- 5 次调用触发 4 次精调，合计 4323 秒，约占会话 4879 秒的 89%。第 18、19、20 次精调各约 1340–1390 秒，降幅依次为 20%、6.6%、1.9%。
- 第 19、20 次 LLM 交来的程序，自举数与上一次精调结果完全相同（10144、9475）。原因有两层：
  - `llm_min` 只比较 LLM 原始程序，抄回的精调结果必然算新纪录；
  - Agent 调用 tuner 时固定 `max_sweeps=1`，而一遍扫描中每个点最多只下降一级阶梯，所以每抄回一次都还能再降。
- 每次精调的 history 中，softmax 候选有 69–96 条，其中 64–94 条做完完整成本估计后，因为不比当前便宜（`rejected='cost'`）被拒；粗评和完整评测合计只有 10–25 次。这些候选来自 `softmax_moves` 对每个 role 枚举 `select_approximation` 的全部可行近似（exp、inv、step_inv、final_inv），其中多数在局部上就比当前近似更深、乘法更多。按 §6.10 之后单次估计约 10–19 秒计，成本估计约占精调时间的四分之三。
- 因此只把扫描改成多遍并不会省时间，每多一遍都要重付这部分估计。必须先减少被拒的估计，多遍收敛和复用才划算。

**改动（仅 r8-v8，新增 `tune_rule="v8-6.14"`，此后默认；`v8-6.11` 和 `v8-pre-6.11` 保留，供回放）。**
1. **剔除被支配的 softmax 近似候选。** 对 `softmax_moves` 中 `kind="approximation"` 的候选，在完整成本估计之前，用 `CountBackend` 分别计算该 role 当前近似与候选近似的局部核开销：乘法深度，以及各类同态运算的计数（与 `program_failures` 相同的单点构造）。候选在深度和每一类计数上都不小于当前近似（含全部相等）即为"被支配"，记一行 `rejected='dominated'`（写出两者的局部开销），跳过完整估计。`steps`、`inv_budget` 两类结构移动和非 softmax 点不受影响，照旧做完整估计。这是与模型无关的规则，不针对某一行或某个 role。

#### 6.18 r8-v10：正值 inv/rsqrt 校准点的 u 改为对数刻度，以及离线重评（Claude 于 2026-10-29，对应 `A1-transformers-s617-summary-20261029T105741-caa3`）

**判断。**
- Qwen 共 16 次完整评测，连同 R0/R1，全部卡在校准 u≈0.9938。来源是 rsqrt 点，例如第 51 行 `mul_19::rsqrt`：声明域 [1093.6, 296305]，heldout 观测 [2009, 190029]。
- 线性 u = |2(x−lo)/(hi−lo) − 1|。对正值、跨度大的点，下端几乎必然接近 1。要 u≤0.90，需要 obs_min ≥ 0.05·hi + 0.95·lo > 0.05·hi；跨度超过约 20 倍的 rsqrt/inv 点无论怎样声明都过不了。
- 它与 r8-v9 的 M 也矛盾。M 的下端是乘性余量 lo/1.5；即使声明域正好等于 M，下端线性 u ≈ 1 − 0.44·lo/hi。lo/hi < 0.225 时必然超过 0.90。
- BERT 的 R0/R1 在 report 上校准 u=0.948，也是同一原因（第 7 行 rsqrt，跨约 9 倍）。
- 这些点用的是相对误差拟合（newton、relative remez）。在域内，误差由相对拟合决定；覆盖余量应按乘性度量，和 M 一致。因此这是判据缺陷，不是 Agent 的失败。

**① 判据（r8-v10，用户决定）。**

#### 6.19 精调余量：对准目标 u=0.80 与精度余量（Claude 于 2026-10-30，对应 `A1-transformers-s618-20261029T112723-87ab` 及其确认结果的离线重算）

**判断。**
- §6.18 重放中，Qwen 7 个精调程序在 heldout 上都可行（33 000–36 000 次自举），但都没有通过 confirm。冻结的是原第 30 次的原始程序，56 800 次自举，比 R0（54 848）和 R1（36 512）都贵。
- 17 次 confirm 评测中，16 次校准 u 在 0.92–0.944，几乎都卡在 `mul_13::rsqrt`，原始程序和精调程序都一样。唯一通过的原第 30 次是 0.79，因为 Agent 在这一点写了更宽的域。
- **u 的来源是余量规则本身。** 精调对准（以及多数 Agent 程序）把域设为 M。对 r8-v10 的对数 u，若 hi = 1.5·cmax、R = hi/lo，u ≤ 0.90 只允许新数据到 hi·R^(−0.05)。`mul_13::rsqrt` 的 R ≈ 459，相当于 1.10·cmax；confirm 最大值是 1.265·cmax（229 226 对 181 205），所以 u = 0.944。M 的乘性余量和 0.90 的位置门限叠加后，可容忍的超出量取决于域跨度，跨度越大越紧。
- 线性刻度也有同类缺陷。跨零且不对称的点，例如校准 [−1, 10]，M = [−1.5, 15]，校准数据自身的 u 已是 0.939。
- **精度也贴边。** v8-6.17 的上限是 heldout logit_rel_err ≤ 1e-2。精调程序 heldout 误差和 confirm 误差对照：
  - 0.0096 → 0.0389，0.0089 → 0.0379，0.0061 → 0.0143；
  - 0.0075 → 0.0062，0.0073 → 0.0059，0.0073 → 0.0060，0.0052 → 0.0028。
  - 20 句 heldout 估计的误差，换一组句子可差 4 倍。
- 方案 2（confirm 只要求校准 u ≤ 1）已离线重算，见 `A1-transformers-s618-20261029T112723-87ab/qwen/plan2-confirm-rescore/`。按"冻结即停"，会话 01 会冻结原第 4 次原始程序（38 752）。它的两个精调程序在 confirm 上因精度不过被拒，所以仍比 R1 贵。用户决定先写本节方案。

**① 精调规则 `v8-6.19`（只改精调器；提示词、反馈、M、confirm、report 判据都不变）。**
