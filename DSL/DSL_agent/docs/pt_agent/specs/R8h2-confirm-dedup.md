## 0. 诊断（Claude 于 2026-10-24 复核 R8h 的 ResNet20 确认失败）

- ResNet20 的候选池有 8 项，确认按预测延迟从低到高，最多 6 次。实际做的 6 次确认中，有两对是**同一个程序**：
  - 第 3 轮 tuned 与第 4 轮 llm（209 次自举）；
  - 第 2 轮 tuned 与第 3 轮 llm（216 次自举）。
  
  这是因为 LLM 下一轮会原样交回上一轮精调后的程序。6 次确认实际只覆盖了 4 个不同的程序，第 1 轮 llm（325 次自举）没有被检查。
- 被检查的 4 个程序在确认集上都有 1 张图发散，acc_drop 为 0.6–1.4pp，均未通过 ≤0.5pp。
- 重复是 R8h"对每个候选都精调"带来的新情况，需要通用修复。

## 1. 修改 `planners/confirm.py`（冻结模块，本 spec 明确授权修改）

`confirm_select(pool, ctx, ...)` 排序之前先去重：

1. 键为规范化后的程序文本 `print_program(parse(source))`；
2. 同一个键只保留一项：保留排序后最先出现的那项，同延迟时按 pool 中的原始顺序；其余记入 `duplicates`，包括被合并项的 iteration 和 origin；
3. `MAX_CONFIRM_EVALS` 按**去重后的不同程序**计数；
4. 返回结果中增加 `deduplicated`（去重前后的数量）和 `duplicates` 列表；
5. 通过判据、排序规则、`MAX_CONFIRM_EVALS=6` 和确认集都不变。

`agent.run` 不需要修改；如果 records 的键因去重需要调整，只做最小的适配，并在汇报中说明。

## 2. 测试（新增 `tests/test_r8h2_confirm_dedup.py`）

1. pool 中有 2 个相同的程序（origin 不同）加 1 个不同的程序：只做 2 次确认，`duplicates` 记录了被合并的一项。
2. 去重后不同程序的数量少于 `MAX_CONFIRM_EVALS` 时，全部被检查到。
3. 在无重复的 pool 上，结果与修改前逐项相同。
4. 规范化：仅空白和缩进不同的同一程序视为重复。
5. 既有 362 项测试全部通过。
